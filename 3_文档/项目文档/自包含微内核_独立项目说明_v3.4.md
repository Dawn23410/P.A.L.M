## 2. 人格引擎（v1.6）

### 整合了什么

| 原位置 | 内容 |
|---|---|
| 主工程 `palm/domain/roleplay/` | 角色卡模型、双线好感度（规则引擎 + 持久化）、动态叠加、角色污染守卫、Skill 导入 |
| 共享六面 `palm_faces/` | 人格面、情感面、律动面、储存面、档位常量、面骨架、装配器、传输包 |

**冲突处理**：两套 `CharacterCard`（主工程版字段全、CCv2/V3 对齐；六面版是早期简化版）→
**以主工程版为准**，并在其上补 6 个面层兼容字段（`tone` / `age` / `birthday` / `schedule` /
`safety` / `dynamic_updates_enabled`），补 `to_dict`/`from_dict`，使面层零改动即可用。
两套好感度 → 保留主工程的规则引擎 + 结算 + 存储；六面版只留档位常量（`stages.py`）。

### 结构

```

├── character.py       角色卡（VoiceProfile / SceneBrief / CharacterCard）+ 增删查
├── persona_render.py  人设渲染器        ├── skill_import.py  Skill(MD) → 角色卡
├── affection.py       好感度结算        ├── affinity_engine.py  规则引擎(YAML)
├── affinity_store.py  好感度持久化      ├── dynamics_engine.py  动态叠加
├── pollution_guard.py 角色化污染剥离    ├── stages.py  官方 6 阶档位 + 默认卡

├── transport.py       传输包 + 控制码   ├── host.py  宿主适配（主工程在场则复用，否则本地 Data/）

```

### 面的归属（六面取消后）

| 面 | 现归属 | 理由 |
|---|---|---|
| 人格面 / 情感面 | **人格引擎** | 本次整合主体 |
| 律动面 | **人格引擎** | 其 docstring 自述「为人格引擎服务的运行时动态」（原计划给心智核心，发现缝合引擎也在用） |
| 储存面 | **人格引擎** | 三处都导出它；作为面框架的一部分 |
| 织语面 | **缝合引擎**（`local_reply.faces.weave`，实体） | 风格约束是缝合引擎本行；心智核心与 palm-chat 桥接它 |
| 记忆面 | **记忆项目**（`palm_memory.memory_face`） | 早已独立 |
| 中间件（注入契约 + 装配器 + 回复拆分） | **人格引擎** `assembly.py` | 见下方说明 |

> **关于中间件**：原计划给缝合引擎，实际放入人格引擎。原因：`InjectionModule` 是各面产出的
> **数据契约**（人格引擎的面必须依赖它），且心智核心与 palm-chat 也要用装配器 —— 放人格引擎可避免
> 「心智核心 → 缝合引擎」这类上层互依赖。缝合引擎/心智核心/palm-chat 的 `middleware/` 均为薄桥接，
> 调用面（`from middleware.inject import PromptAssembler`）不变。

### 主工程侧

`palm/domain/roleplay/` 的 8 个已迁出模块改为**薄桥接**（`import palm_boot` + 再导出），

### 17.2 评测方法（以及必须披露的局限）

**为什么用检索池而不是全量**：本机 bge-m3（ONNX / CPU）实测 **~130ms/条**，
全量 10 万条要 **~3.6 小时**；且 16GB 内存可用仅 ~2.5GB，**装不下全量语料的字符 bigram 倒排**。
加线程无效（8→16 线程只快 9%，瓶颈是内存带宽）。

故采用「相关文档 ∪ 同语料随机负例」的检索池，**指标偏乐观**（少了 10 万余条天然干扰项），
**不可与 MTEB 等全库榜单直接比较** —— 该声明写进了脚本的 `note` 字段与文档。

**可复现性**：池子构建全程排序后再切片。此前用 `set` 迭代顺序切片，换一次进程就换一批正例
（Python 字符串哈希带随机盐）—— 指标不可复现、嵌入缓存也会失配。

### 17.4 与 LangChain 同条件对比（同一语料包 / 同一批向量 / 同一套指标）

LangChain 1.4.0 + FAISS + rank_bm25，装在 RAG 项目内的隔离环境 `.bench_venv`
（两侧依赖不兼容 → 分两个解释器跑，靠落盘的**语料包**对齐数据与向量）。

| 链路 | Recall@10 | MRR@10 | NDCG@10 | p50(ms) |
|---|---:|---:|---:|---:|
| LangChain FAISS（纯向量） | 0.8987 | 0.9572 | 0.9096 | 44.3 |
| LangChain FAISS + MMR | 0.4259 | 0.9529 | 0.4959 | 56.0 |
| LangChain BM25（字符bigram） | 0.7801 | 0.8902 | 0.7922 | 63.5 |
| LangChain FAISS+BM25 → RRF | 0.8758 | 0.9568 | 0.8879 | 101.5 |
| **P.A.L.M dense（ChromaDB）** | **0.8987** | **0.9572** | **0.9096** | 45.5 |
| P.A.L.M lexical（字符bigram BM25） | 0.7796 | 0.8941 | 0.7955 | **0.9** |
| P.A.L.M hybrid(RRF) | 0.8728 | 0.9597 | 0.8869 | 42.0 |
| **P.A.L.M hybrid+rerank（pool=20）★** | **0.9045** | **0.9657** | **0.9178** | 3299 |

三条结论：

1. **实现互校通过**：本引擎 dense（ChromaDB）与 LangChain FAISS 在 Recall/MRR/NDCG 上
   **四位小数完全一致** —— 两条独立实现的检索语义一致，对比才成立。
2. **MMR 是召回陷阱**：`FAISS + MMR` 的 Recall@10 掉到 0.4259（Hit@1 仍 0.945）——
   它优化的是"结果多样性"而非"相关度"，直接拿来当检索器会重伤召回。
3. **只有「混合+重排」在所有指标上超过纯稠密**，代价是延迟 45ms → 3.3s（约 73 倍）。
   是否值得是产品决策，数字摆在这里。

### 17.5 深度诊断：RRF 融合的价值在"深处"，不在 top-10

只看 k=10 会得出**错误结论**（融合反而低于纯稠密）。把三条链路在多个截断深度上并排看：

| 链路 | R@10 | R@20 | R@50 | R@100 |
|---|---:|---:|---:|---:|
| 纯稠密 | **0.8987** | 0.9316 | 0.9476 | 0.9664 |
| 纯词法 BM25 | 0.7796 | 0.8317 | 0.8838 | 0.9058 |
| 混合 RRF | 0.8716 | 0.9379 | **0.9648** | **0.9777** |

k=10 融合低于纯稠密（RRF 按秩求和会把稠密的头部挤下去），**k≥50 起明显反超**。

**因此「混合检索 + 重排」是一对必须成对使用的组合**：融合负责把答案拉进候选池，
重排负责把它提到前面。只用融合，反而比纯稠密差 —— 这是本轮最重要的架构结论。

配套诊断行「融合候选池@100」即用来量化重排前的召回天花板（池 20 时上限就是 R@20）。

### 17.6 数据清洗（四道工序 + 全量审计）

新增 `palm_rag/cleaning.py`：**HTML/实体剥离 → 异常过滤（空/过短/过长/乱码/低信息）
→ 精确去重（SHA1）→ 近重复（SimHash + 汉明距离，分桶避免 O(n²)）**，
清洗过程**可审计**（每道工序丢多少、为什么，都记在 `CleanReport`）。

|---|---:|---:|---:|---:|---:|---:|
| **T2Retrieval** | 118,605 | **65.74%** | 1.07% | 0.74% | 116,458 | **85.3%** |
| DuRetrieval | 100,001 | 0.40% | 0.25% | 0.37% | 99,373 | 96.8% |
| CovidRetrieval | 100,001 | 0.43% | 0.23% | 0.34% | 99,429 | 97.4% |

**两个结论**：① T2Retrieval 是重度 HTML 污染，剥离后字符量掉 14.7%，不清洗会把

### 17.7 本轮修掉的两个真实缺陷

| 缺陷 | 证据 | 修复 |
|---|---|---|
| `LexicalIndex.build` 用 `for g in set(grams)` 建倒排 → **每个 gram 的 tf 恒为 1**，BM25 的饱和项 k1 完全失效 | 词法 Recall@10 = 0.7302，而同分词口径的 LangChain `rank_bm25` = 0.7801 | 改为遍历**含重复**的 grams；修后 **0.7796**，与参考实现差 **0.0005** |
| `simhash` 每个 bigram 一次 md5 + 逐 bit 双层 Python 循环（每文档约 5.5 万次解释器循环） | **5.29 ms/文档** → 全量 11.8 万条要 10 分钟、6 数据集要 1 小时，全量清洗实际不可用 | 改 numpy 向量化（字符码乘法散列 + (n,64) 位矩阵求和）→ **0.30 ms/文档（17.8×）** |

simhash 重写做了**判别力等价验证**：随机对汉明距离均值 29.96 → 30.36（理想 32）；
「改 1 字」判为近重复 93.2% → 93.2%；无关文本误判 0.0% → 0.0%；确定性同输入同输出。
验证脚本 `P.A.L.M -1/.workbuddy/tmp/verify_simhash.py`。

另修一个工程坑：`embed_cache` 收尾删断点文件时被环境的"批量删除需确认"安全钩子拦截，
导致**嵌入跑完 24 分钟后在最后一行崩溃**（缓存其实已落盘，纯属收尾动作拖累）。
已改为非致命清理。

### 17.8 重排默认值按实测定（`rerank_max_chars = 384`）

`bge-reranker-v2-m3` 本机约 1500 token/s、`max_len` 封顶 512，故延迟与送入 token 总量成正比。
20 个真实长度候选：**不截断 6,612ms / 384 字 3,752ms / 192 字 1,896ms**。

质量消融（588 文档池 / 20 查询）：Recall@10 = 0.9582 / **0.9582** / 0.9532，
NDCG@10 = 0.9750 / 0.9735 / 0.9704。

**结论：截到 384 字指标无损、延迟降 1.76 倍** → 定为 `engine.query` 默认值
（`rerank_max_chars=384`）；再截到 192 字开始掉点。消融池较小，属初步证据，换域建议复测。

### 17.9 意外发现：嵌入向量依赖批次组成（重要）

做**重构等价性验证**时发现的：同一配置复跑，5 条链路里 4 条逐位一致，
只有 `重排 pool=20` 的 NDCG@10 差 0.0003。逐层排查：

| 检查 | 结果 |
|---|---|
| 重排器 3 次同输入 | 分数**逐位相同**、顺序相同 → 确定性没问题 |
| 查询嵌入 4 次 | **逐位相同** |
| 同一文本「单条嵌」vs「批内嵌」 | **最大分量差 1.57e-2** —— 且**不是 padding 造成**（批内陪衬更短、本体未被 padding 也差） |

**结论：bge-m3 的 ONNX 导出下，同一文本的向量会随批次组成变化**（推测是 int8 动态量化
的激活缩放按批统计，未逐图验证）。

**关键影响**：RAG 的真实用法是**灌库按批（batch=32、按长度排序）、查询单条** ——
查询与文档向量落在**不同量化区间**。量化到检索层面（`bench/batch_dependence.py`，
9,854 文档池 / 40 查询）：

| 项 | 结果 |
|---|---|
| 查询向量最大分量差（单条 vs 批内） | 中位 1.78e-2，最大 2.80e-2 |
| **top-10 重合度** | **中位 90%，最差 70%** |
| Recall@10 | 单条 0.8978 / 批内 0.9049（**无系统性损失**） |

**判读规则**：精度没坏，但结果**不可逐位复现** → **基准指标差异 < 0.001 一律当噪声**。
同时给嵌入缓存指纹**加上 batch 参数**（否则换 batch 会静默复用另一套协议的向量）。
