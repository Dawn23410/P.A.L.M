## 2. 优化了什么（以及为什么）

优化前实测（20,000 条 / 45.9MB）：整条清洗管线 **5.6 MB/s**。

### 2.1 算法层（v1.0，纯 Python+NumPy：5.6 → 21.5 MB/s）

| 根因 | 修法 | 实测 |
|---|---|---|
| 无条件跑全部正则/规范化 | **廉价先探测**（`'<' in t` 是 C 速度、13 GB/s 量级） | 46.8 → 55.7 |
| 异常判定逐字符调 `unicodedata.category()` | numpy **码点查表**（1.1MB bool LUT） | 16.0 → 168.6 |
| SimHash 每 shingle 摊开 64 位（O(64n)） | **OPH**（One Permutation Hashing，O(n)） | 8.7 → 124 |

两次"越改越慢"（都靠 profile 定位，详见 §5）：KMV 骨架配错估计量 → 候选爆炸；
高频 bigram 的固定散列污染倒排桶 → **正解都是 OPH 的位置语义 + 分带**。

### 2.2 C 层机器码（v1.1，numba JIT：21.5 → 47.09 MB/s）

numba 把「逐元素循环」编译成机器码，吃掉 numpy 的**每次调用固定开销**
（1-2µs/次，单文档 ~35 次调用 = 35-70µs —— 这就是单核吞吐的主要天花板）。
四个热路径全部替换，**缺失 numba 时自动回退 numpy 实现（功能等价）**：

| 热路径 | NumPy 现状 | numba 单遍 | 提升 |
|---|---:|---:|---:|
| 异常判定（查表 + 垃圾字符统计） | 154 MB/s | **1132 MB/s** | 7.3× |
| OPH 骨架（bigram 哈希 + 分桶取最小） | 85 MB/s | **685 MB/s** | 8× |
| 归一化（全角/控制符/空白/换行/标点 4 条正则链） | ~93-100 MB/s | 单遍扫描 | ~2× |
| HTML 标签剥离（交替正则 + 回调） | 326 MB/s | 单遍扫描 | ~2× |

**替换的验收口径**（全部实测）：
- OPH 骨架与 numpy 版**逐位一致 300/300**；
- 异常判定 verdict 一致 **300/300**；
- 归一化输出与原 4 条正则链**逐字符一致 8000/8000**（修掉两个实现 bug 后，见 §5）；
- HTML 剥离等价率 **98.4%**，剩余 1.6% 是正则版把 `<a>` 内嵌套的 `<img>` **泄漏进正文**、
  numba 版将其剥掉 —— numba 版更干净，已在代码注释中声明；
- 近重复判定质量不变：无关对 **0/2000 误杀**、轻微改写 **100% 检出**。

## 4. 并发架构（100 份并发）

`palm_rag/ingest.py`（队列内核）+ `palm_rag/ingest_api.py`（服务壳，端口 10091）：

```
上传 → POST /texts|/files ──► 有界队列（在途 ≤100，满了 429 背压）
                                 │
                                 ├─► 进程池（默认 8 进程，清洗+分块）
                                 │      └─ 完成 → 状态 searchable（词法即可检索）
                                 └─ 稠密向量由调用方异步补（CPU 上嵌入慢 4 个数量级）
```

### 4.1 四个必须的设计点（全部实测踩出来的）

| 设计点 | 不做会怎样（实测） |
|---|---|
| **后台收割线程** | 没人调 `poll()`，作业状态永远停在 running |
| **收割收敛到单点** | 调用方与收割线程同时扫 `_futures` → 同一 future 被两边 pop，**KeyError**（100 并发必撞） |
| **启动时预拉满工作进程** | 惰性拉进程 + Windows spawn 0.3-0.5s/个串行 → 100 并发首涌 p50 从 1s 恶化到 9.8s |
| **池惰性创建 + 加锁** | Windows spawn 让子进程重新 import 主模块 → 模块级建池=无限递归；并发首请求无锁各建一个池 → **实测 53 个残留进程，health 都超时** |

### 4.2 压测结果（100 份同时上传，numba 后）

| 指标 | 首轮（含 JIT 加载） | **热态** |
|---|---:|---:|
| 提交 | 3.1 ms/份 | **1.1 ms/份** |
| 服务端处理 | p50 1251ms | **p50 16ms / p95 32ms / max 34ms** |
| 全部消化 | 1.31s（76 份/s） | **0.23s（444 份/s）** |
| 完成/拒绝/失败 | 100/0/0 | **100/0/0** |

首轮的 1.3s 是**一次性 JIT 加载**（工作进程首次加载编译缓存），服务常驻后不再出现。

## 5. 本轮修掉/踩掉的四个坑

1. **KMV 骨架配 k-独立置换版估计量**：逐位相等比较套在 bottom-k 上 → 每篇 281 个候选
   （`jaccard_est` 调 139 万次），近重复占整线 61% 时间而 2 万条只找到 4 条。
2. **标点折叠冲刷条件写错**：`if p_len >= 2: 输出 b1` 对 L≥3 也生效 → `...` 折成了 `..`。
   正确语义是 L≥3 只留首字符、L=2 原样 —— 差一点就带着 bug 交付（8000 条逐字符校验抓出来的）。
3. **`\t` 漏出空白折叠**：`&#9;` 实体折叠成真 tab 后，空白类检查只写了 `c == 0x20`，
   tab 被当普通字符透传。
4. **HTML 标签替换必须补空格**：`<td>a</td><td>b</td>` 的空格是内容分隔符；
   numba 版最初直接吞标签 → 相邻内容粘成一词，63.5% 的 HTML 文档与正则版不一致。

## 6. 性能开销曲线（numba 后，最佳点）

扫三组维度（语料 31.5MB / 13,708 条 / 300 份作业）。产物：
`bench/results/cost_curve.json` + **`bench/cost_curve.html`**（四张图，直接打开看）。

**① 吞吐 vs 核数**（在途 100）

| 进程数 | 1 | 2 | 4 | 6 | 8 | **12** | 16 |
|---|---:|---:|---:|---:|---:|---:|---:|
| MB/s | 27.69 | 54.07 | 87.83 | 119.87 | 121.92 | **129.85** | 121.98 |
| 每核 | 27.69 | 27.04 | 21.96 | 19.98 | 15.24 | 10.82 | 7.62 |

**② 延迟 vs 在途数**（12 进程）

| 在途 | 1 | 4 | 16 | 64 | 100 | 200 |
|---|---:|---:|---:|---:|---:|---:|
| MB/s | 3.26 | 12.96 | 47.92 | 120.97 | **139.29** | 122.86 |
| p50 延迟 | 16ms | 16ms | 16ms | 37ms | 47ms | 123ms |
| p95 延迟 | 32ms | 32ms | 39ms | 68ms | 96ms | 171ms |

**③ 吞吐 vs 每作业条数**（12 进程）：1 条 = **2.54 MB/s**（进程间开销淹没一切），
16 条 = 73，**64 条 = 137.95（最优）**，256 条 = 108 → **≥64 条/作业才摊薄，64 最优**。

**④ 机器并行上限对照**：同核数纯 CPU 循环实测 3.17×-4.44×（该探针自身受热节流影响、
噪声较大），管线 4.74× —— **与机器并行能力同量级**，并行度已吃满。

### 最佳点

> **吞吐优先：12 进程 / 在途 64-100 → 121-139 MB/s（p95 68-96ms）**
> **延迟优先：8 进程 / 在途 16 → p95 39ms（47.92 MB/s）**
> 吞吐饱和点 ≥85% 峰值的最小核数 = 6 进程（119.87）；12 进程是峰值；16 回落。
> **每作业 ≥64 条文档**是最优批大小（1 条/作业 = 2.54 MB/s，全被进程间开销吃掉）。

## 7.5 性能开销监控与资源限制（v1.1 后补）

### 监控

新增 `palm_rag/metrics.py`（线程安全指标注册表，~110 行，自研不上 Prometheus client —— 需要的
只是进程内几十个指标 + 滚动分位，引客户端库会把 /metrics 格式绑死）：

- **计数器**：jobs_submitted / accepted / completed / failed / rejected、texts_in / dropped、chunks_out
- **延迟分位**（每序列保留最近 512 个样本）：text_ms（作业处理）、wait_ms（排队）、
  stage_clean_ms / stage_chunk_ms（阶段耗时，由工作进程随结果带回）
- **窗口吞吐**：60s 滑动窗口的 份/s 与 MB/s（事件级记录，按窗口淘汰）

端点：`GET /metrics`（JSON）、`GET /metrics/prometheus`（文本格式）、
**`GET /dashboard`（自包含 HTML 仪表盘，Chart.js 1s 自刷新：吞吐 / 延迟 / 阶段耗时 / 在途与积压）**。

### 限制（全部环境变量可调，超限明确报错而非静默丢弃）

| 限制 | 环境变量 | 默认 | 超限 |
|---|---|---:|---|
| 在途作业数 | `PALM_INGEST_INFLIGHT` | 100 | 429 |
| 在途字节（内存护栏） | `PALM_INGEST_BACKLOG_MB` | 512 | 429 |
| 单次提交条数 | `PALM_INGEST_MAX_TEXTS` | 500 | 400 |
| 单篇字符数 | `PALM_INGEST_MAX_CHARS` | 200 万 | 413 |
| 单文件大小 | `PALM_INGEST_MAXMB` | 32 | 413 |

**顺手修掉一个静默丢数据的 bug**：`clean_corpus` 的"过长"阈值默认 8000 字，
摄取服务把整篇上传文档当一行清洗 —— 一份 10 页 PDF（>8000 字）会被整篇丢成
`too_long`。修复：摄取路径把该阈值放大到文档级（200 万），嵌入安全由「清洗后再分块
（≤500 字/块）」保证；入口处的 413 上限负责拒绝真正的畸形文件。验证：1.5 万字文档
清洗+分块 0.8ms（热态），32 块，不再被丢。

**首笔延迟优化**：惰性池把「拉起 8 进程 + JIT 编译」攒到第一个请求（实测首笔 1.2s）。
改为启动时后台预热线程 → **首笔端到端 19ms**（热态 14ms）。

### 7.5.1 档位预设：eco（默认）与 std

服务常驻内存的大头是**每个工作进程各自加载的 numpy/numba/JIT 产物（~500MB/进程）**
—— 8 个 worker 空转就是 4.6GB（§7.6 空闲基线）。日常单人使用根本用不满 8 进程，
所以默认档位改为 **eco：单工作进程 + 3 并发**，把常驻内存砍 ~97%：

| 预设 | 环境变量 | worker | 在途 | 积压上限 | 稳态内存（USS 实测） |
|---|---|---:|---:|---:|---|
| **eco（默认）** | `PALM_INGEST_PROFILE=eco` | **1** | **3** | **64MB** | **141 MB** |
| std | `PALM_INGEST_PROFILE=std` | min(8,核) | 100 | 512MB | 4.62 GB |

- 显式环境变量（`PALM_INGEST_WORKERS/INFLIGHT/BACKLOG_MB`）**永远优先于预设**。
- 限额水位与档位随 `/health`、`/metrics`、仪表盘透出（profile / workers 字段）。
- 验证：连发 8 笔 → 前 3 笔 200（在途 3），后 5 笔 **429**；completed 3 / rejected 10；
  稳态 USS 141MB（负载后不变）。
- **顺手修一个 bug**：背压拒绝路径调用了不存在的 `self._metric_incr` → 拒绝时抛
  AttributeError 变 **500** 而不是 429。已改为 `self.metrics.incr(...)`（带 None 保护）。

## 7.6 多档位实测开销（空闲 / 平常 / 中载 / 满载）

`bench/tier_load_test.py` 按真实使用形态分四档，**每档按时长持续加载**（12-20s 稳态采样，
不是跑 0.2s 就停），psutil 以**持久进程对象**采样服务进程树（主进程 + 8 工作进程）。
数据：`results/tier_load.json` + **`bench/tier_load.html`**（四张对比图）。

| 档位 | 负载 | 吞吐 | 延迟 p50/p95 | CPU（均/峰） | 内存 USS（均/峰） |
|---|---|---|---|---|---|
| T0 空闲 | 无 | — | — | 0% / 0% | **4.62 GB / 4.62 GB** |
| T1 平常 | 2 并发 × 单篇 15.4KB | 24.5 份/s | 64 / 171ms | 24.6% / 0.86 核 | 4.63 / 4.63 GB |
| T2 中载 | 10 并发 × 5 篇 15.4KB | 94.6 份/s（7.1 MB/s） | 94 / 203ms | 100% / 2.04 核 | 4.88 / 4.88 GB |
| T3 满载 | 16 线程 firehose × 10 篇 25.9KB | 73.5 份/s（**18.6 MB/s**） | —（提交-only） | 328% / 4.54 核 | 6.54 / **6.54 GB** |

全部 0 失败 0 拒绝。三个结论：

1. **服务常驻的真实成本 = ~4.6GB 独占内存 + 0% CPU**。空闲 4.6GB 主要是 8 个工作进程
   各自加载的 numpy/numba/JIT 编译产物（进程间共享页在 RSS 合计里会重复计，
   所以 RSS 合计 6.8GB 是虚的，USS 才是真实占用）。
2. **平常档几乎免费**：CPU 峰值 0.86 核，延迟 p50 64ms —— 单人日常使用感知不到。
3. **满载瓶颈在 HTTP 层**：firehose 实测 18.6 MB/s，而同机器**无 HTTP** 的池内直测是
   129 MB/s（§6）—— 差距 ~7×，来自每请求 ~13ms 的 Windows HTTP 地板价 + JSON 编解码 +
   进程间序列化。**要吃满池能力，走批量接口（每作业 ≥64 篇）或进程内调用**，
   单篇小文档走 HTTP 的上限就是 ~20-25 MB/s。

### 档位实测的三个测量陷阱（本轮踩的）

- **残留服务实例污染测量**：4 个昨天的遗留实例（各 ~4.8GB）抢 CPU/内存，
  把 T1 吞吐从 31 污染到 16.7 份/s。清场守卫按**端口**判单实例
  （cmdline 判不行 —— venv 的 python.exe 是 shim，一层套一层会误判）。
- **CPU 采样必须持久进程对象**：psutil 的 cpu_percent(None) 是「该对象上次调用以来」
  的差值，每次新建对象差值基准就丢了（首轮出现过 233 核的荒谬值）。
- **RSS 合计虚高**：9 个进程共享同一份库，合计会把共享页重复计 2-3×，
  必须用 USS（独占内存）才反映真实占用。
