## 二、A. Reranker / Cross-encoder 精排（最高 ROI）

### 为什么它正对我们的病

我们的核心失败模式是**语义错配假阳性**：`安慰我` → "午安呀，你吃饭了吗"、
`帮帮我` → "你好呀，今天怎么有空"。原因就是 bi-encoder 的固有缺陷——
query 和候选各自编码，**从不见面**，只能靠向量距离"脑补"。

Cross-encoder 把 query+候选拼在一起走完 attention，每个 query token 对每个候选 token 都交互。

### 公开数据 [搜]

| 流水线 | NDCG@10（BEIR 均值） |
|---|---|
| BM25 only | 41.7 |
| Bi-encoder (BGE-base) | 51.0 |
| **Bi-encoder + Cross-encoder rerank** | **56.5** |
| Bi-encoder + GPT-4 rerank | 58.2 |

Rerank 带来 **+5~15 NDCG 点**，是 RAG 栈里单步收益最大的改动。

另一个实测案例：某知识库只用向量检索 Recall@3 = 0.61；加混合检索后 Recall@20 = 0.91
但 Recall@3 只有 0.68；**再加 cross-encoder 重排，Recall@3 冲到 0.86**——多 100ms 换 25 个百分点。

### 模型候选 [搜]

| 模型 | 参数 | 体积 | 特点 |
|---|---|---|---|
| `cross-encoder/ms-marco-MiniLM-L6-v2` | 22M | 90MB | CPU 单条 5–10ms，**英文-only**，中文弱 |
| `mxbai-rerank-base-v1` | 184M | ~700MB | edge / 最低延迟 |
| `jina-reranker-v2-base-multilingual` | 278M | ~1.1GB | 延迟敏感、多语言 |
| `BAAI/bge-reranker-v2-m3` | 568M | 1.2GB | **中文第一梯队，MIT，最稳的默认选** |
| `Qwen3-Reranker-0.6B` | 595M | ~1.2GB | 指令感知、32K 上下文、多语言 |
| `jina-colbert-v2` | 137M | — | 迟交互，文档侧可预计算 |

### 落地设计（针对我们 733 条语料的小库）

```
query → bge-m3 召回 top-20（52ms）
      → 若 top1 与 top2 语义分差 < 0.03（存疑），才触发 rerank
      → cross-encoder 对 20 个候选打分 → 取 top1
      → 分数 < 阈值（bge 用 0.3）→ 判为不相关，直接走降级兜底
```

关键点：**只对存疑句触发 rerank**。按我们的数据，约 20–30% 的 query 会触发，
其余维持 52ms，均摊延迟增量 ~50ms。同时"低分直接丢弃"这一条能**堵住 `帮帮我` 这类新假阳性**。

## 三、B. 更小的 Embedding 模型

### 现状问题

bge-m3 是 567M / 1024 维 / MTEB 66.0，对 733 条短句的中文口语匹配**明显过度配置**。

### 候选对比 [搜]

| 模型 | 参数 | 维度 | MTEB | CPU 单句 |
|---|---|---|---|---|
| BAAI/bge-m3（在用） | 567M | 1024 | 66.0 | 15.6ms（本机遇测）/ 120ms（i5-1135G7 测） |
| BAAI/bge-small-zh-v1.5 | 24M–100M | 512 | 58.3 | ~28.6ms（i5-1135G7） |
| shibing624/text2vec-base-chinese | 102M | 768 | 54.8 | ~68ms |
| Alibaba-NLP/gte-small | 33M | 384 | 61.2 | — |
| all-MiniLM-L6-v2 | 22M | 384 | 58.8（英文） | 11.2ms |

注意：不同来源对 bge-small-zh 的参数量说法不一（24M vs 100M），实测前需确认具体 checkpoint。

### 建议

`bge-small-zh-v1.5` 做**粗筛**（~15–28ms 出 top-20）+ `reranker` 做精排。
小模型粗筛丢了精度，由 reranker 补回来，总体比"大 embedding 单打独斗"又快又准。
这是业界标准的两级架构，不是折中。

## 四、C. 小生成模型做兜底（解决"直接说不会"）—— ⚠️ 已推翻，保留作为反例

> **2026-09-06 修正：本节原推荐 Qwen3-0.6B 等亚 1B 模型做兜底生成，经查证该判断错误，已推翻。**
> 保留原文并附反证，避免重蹈覆辙。

### 我们的死穴

即使开了语义检索，T3 仍有 16%、T4 仍有 43% 的句子**直接降级**（"去问 LLM 吧"）。
4 条兜底文案轮播，连续两句未见就聊崩。

### ~~2026 年可用的 CPU 小模型~~ → 判死刑的证据 [搜]

| 反证 | 内容 |
|---|---|
| **XSCT Bench 对话创作实测** | Qwen3-0.6B 得分 **18.8，判定"未通过"**。三个 judge 一致差评："候选输出质量极低，三个核心维度均严重不达标"；**人设一致性与语调 12/100、指令遵循 8/100、场景自然度 18/100**；"角色塑造方面，两人风格无差异，身份背景完全缺失" |
| **官方模型卡缺点** | "0.6B scale significantly limits reasoning depth, factual accuracy, and **coherence**"；"**Prone to repetition and hallucination** on complex or multi-step instructions"；"**Outperformed by most 1-3B alternatives** on benchmarks" |
| **正面案例的真实条件** | 那篇"Qwen3-0.6B 游戏 NPC 对话"实测用的是 **A10G 24GB GPU**、7 实例并发、首字 0.83s——**不是 CPU 场景**，且是镜像推广文 |

**人设一致性 12/100** 这一项直接判死刑：我们要的恰恰就是人设一致。
0.6B 做不了角色扮演生成，更做不了"四要素 + 猫娘口吻"的结构化输出。

### 修正后的判断

- **亚 1B 模型：不能用于人格化生成**，连"改写检索到的回复"都勉强（指令遵循 8/100）。
- 若要兜底生成，**下限是 1.5B–3B**（LFM2.5-1.2B 勉强、Qwen2.5-3B 更稳），
  且 CPU 上 13.5 tok/s → 一句 25 字约需 2–3 秒，**与"极小开销"定位直接冲突**。
- 结论：**C 方案从路线图里降级**。在 RTX 5060 上可跑，但那就不是"零 GPU 确定性桩"了，
  是另一条产品线。

### 架构验证：混合方案已被论文证实 [搜]

> "The Correct Architecture: Use a traditional behavior tree for strategy and high-level
> decision-making. Use the tiny model only for dialogue generation and flavor text."
> —— Fixed-Persona SLMs with Modular Memory（arXiv, Nov 2025）
>
> 结论：<1B 模型 **不能做规划**，但**能做对话生成**；
> TinyLlama-1.1B 全响应延迟 1.91s，首字 <0.2s——对有"思考动画"的交互完全够用。

**这正是我们的架构**：确定性引擎 = 行为树，小模型只负责"怎么说"。

### 落地设计（保守版）

```
检索失败 → 取语义最相近的 3 条 (q, reply) 作为 few-shot
        → prompt = 人格卡 + 3 个样例 + 用户 query
        → 小模型生成 1 句猫娘风格回复
        → 硬约束：长度 ≤40 字、必须含四要素、禁输出事实性断言
```

### 风险（必须写明）

**这一条会破坏"零幻觉"这个当前最大优势。** 小模型生成必然偶发胡说。
建议只在"情绪安慰类"开放（如"被领导骂了"→ 生成安慰话，说错也无害），
事实类（时间/天气/知识）继续走确定性工具或降级。

## 五、D. 难负例微调 Embedding（美团实践）[搜]

美团检索式对话系统的工程结论，对我们直接可用：

1. **必须用 QQ 召回，不能用 QA**。
   > "如果 Context 是'谢谢'，向量检索返回的大多是感谢语义的句子，
   > 然而我们应该召回回复感谢的'不客气'。实验表明 QA 召回远差于 QQ 召回。"
   > **我们当前正是 QQ**（用 query 匹配 corpus 的 q 字段）—— 已做对。

2. **负例构造**：batch 内简单负例 + BM25 难负例，经验比例 **100:1**。
   两种挖法：CBM（用 Context 索引挖相似 Context）、RBM（用 Response 索引挖）。

3. **双塔 DualEncoder > BERT 平均池化 > BoW**。

4. 完整架构是**五层**：数据 → 召回（文本+向量+知识多路）→ 排序（规则+相关性模型+CTR）
   → 策略（重排/拒推/多样性）→ 应用。
   **我们目前缺"排序层"和"策略层"**——这是 A 方案的理论依据。

用我们 733 条语料 + BM25 挖难负例微调 bge-small-zh，是零数据成本、一次性的投入。

## 六、E. ONNX int8 量化 [推]

bge-m3 当前是 570MB fp32 ONNX。动态量化到 int8：
- 体积 570MB → ~150MB
- CPU 推理通常 **2–4× 加速**（15.6ms → 5–8ms）
- 语义检索精度损失通常 <1%（短句场景）

零代码改动，只需重导出 ONNX 并换文件。**这是性价比最高的一步，应先做并实测。**
