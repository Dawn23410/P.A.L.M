> 日期：2026-09-06

## 一、量化：模型早就是 int8，此路不通

检查 `bge_m3.onnx` 的 initializer 数据类型：

| dtype | 张量数 | 体积 |
|---|---|---|
| INT8 | 288 | 302.2 MB |
| UINT8 | 6 | 264.4 MB |
| FLOAT | 389 | **2.2 MB**（仅 LayerNorm 等） |

**570MB 里 566MB 已经是 int8/uint8。** 再量化收益≈0。

我在《技术选型调研》里写的"int8 量化：570MB→150MB、2–4× 加速"是**错的**——那条是通用结论，
没先检查模型现状。已订正。

## 二、真瓶颈：不是模型推理，是纯 Python 点积

### 延迟剖析（优化前，733 条索引）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| respond 总计 | 45.9 ms | 100% |
| embed（模型推理） | 14.7 ms | 32% |
| **点积检索**（733×1024 纯 Python 循环） | **30.4 ms** | **66%** |
| 缝合 / 改写 / 人格 | 0.8 ms | 2% |

`_sem_search` 用 `[cosine(qv, v) for v in index]` 逐条算，733×1024 = 75 万次 Python 循环。

### 修复

改成 numpy 矩阵点积（向量已 L2 归一化，点积即余弦，**数值等价**）：

```python
scores = mat @ np.asarray(qv, dtype=np.float32)   # mat 缓存为 (N,1024) float32
idx = np.argpartition(-scores, k-1)[:k]
```

失败静默退回纯 Python（保持零依赖场景不崩），`self._sem_matrix` 延迟构建、进程内复用。

### 结果

| | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 点积检索 | 30.4 ms | **1.07 ms** | **28×** |
| respond 总计 | 45.9 ms | **15.2 ms** | **3×** |
| 磁盘 / 精度 | — | 不变 | 零代价 |

**正确性验证**：复跑 v3.3 同题对照，命中数完全一致
（T2 30/30、T3 54/56、T4 44/68），零回归。

> 附带发现：v3.3 脚本里"semantic=358ms"是**首次 ONNX session 加载（1645ms）摊到 4 条样本**的假象，
> 稳态真实值是 15.2ms。该脚本的延迟测量缺少预热，需修。

## 三、泛化：语料规模是最强杠杆（且几乎免费）

点积从 30ms 降到 1ms 之后，**扩大语料的检索成本几乎归零**，
这让"扩语料"从昂贵方案变成白捡。

### 规模-命中率曲线（未见句 68 条，阈值 0.72，5 次采样取均值）

| 语料规模 | 未见句命中 | 高频句命中 |
|---|---|---|
| 100 | 19.4% | 44.6% |
| 200 | 36.8% | 62.9% |
| 300 | 45.0% | 71.8% |
| 450 | 53.8% | 80.7% |
| 600 | 57.4% | 86.8% |
| **733（当前）** | **60.3%** | **89.3%** |

拟合：`unseen_hit ≈ 0.2057 × ln(N) − 0.7352`

| 外推规模 | 预计未见句命中 |
|---|---|
| 1000 | ~68.5% |
| 1500 | ~76.9% |
| 2000 | ~82.8% |

> ⚠️ **外推警示**：对数模型在饱和区会失效，外推到 3000(~91%)/5000(~100%) 是**数学artifact，不可信**。
> 真实世界有长尾，覆盖率不可能到 100%。可信区间只到 2000 条左右。

### 为什么扩语料治本，降阈值治标

| 手段 | 机制 | 代价 |
|---|---|---|
| **扩语料** | 把"未见句"变成"见过的句"，**抬高 top1 分数本身** | 索引内存 +3MB/1000条，点积 +1.4ms/1000条 |
| 降阈值 | **放宽门槛**放更多低分结果进来 | 假阳性（错配）线性增加 |

阈值扫描（全量 733）：

| 阈值 | 未见句 | 高频句 |
|---|---|---|
| 0.60 | 95.6% | 98.2% |
| 0.64 | 85.3% | 98.2% |
| 0.68 | 75.0% | 92.9% |
| **0.72（当前）** | 60.3% | 89.3% |
| 0.76 | 39.7% | 82.1% |

降到 0.64 能多召回 25pp，但那批新增的 top1 分数落在 0.64–0.72 区间，
按现有盲评经验 GOOD 率只有 30–40%，**净增有限且假阳性变多**。

## 四、开销账（对照 0.5B LLM 预算）

| 项 | 0.5B LLM（如 Qwen3-0.6B Q4） | 我们（当前） | 我们（扩到 1500 条） |
|---|---|---|---|
| 常驻内存 | ~500 MB | ~600 MB（bge-m3 int8） | ~603 MB |
| 单次延迟 | ~1 s（CPU 20–30 tok/s） | **15.2 ms** | **~16.5 ms** |
| GPU | 不需要 | 不需要 | 不需要 |
| 磁盘 | ~500 MB | 573 MB | 576 MB |

**结论：内存与 0.5B LLM 基本持平，延迟快 60 倍以上。扩到 1500 条仍在预算内。**

若要把内存也压到 100MB 级，需换 `bge-small-zh`（MTEB 58.3 vs 66.0）——
但那会**削弱泛化**，与本次目标冲突。**建议保留 bge-m3**。

## 七、补洞实测：60 条定向语料的真实收益

按第五章的空洞类别清单，编写 `corpus/mengyao_hq_part16.jsonl`（**60 条，同类场景不同措辞**，
不用测试句原句），加入语料后重建索引（733 → 793 条）复测：

| 测试集 | 补洞前 | **补洞后** |
|---|---|---|
| T2 最小改写 30 | 30 | 30（持平） |
| T3 真实高频句 56 | 54 | **55** |
| T4 未见新句 68 | 44 | **65（95.6%）** |
| mock 对照（T4） | 17 | 28 |
| 点积延迟（793 条） | 1.07 ms | ~1.2 ms（无感） |
| respond 延迟 | 15.2 ms | ~16 ms（无感） |

剩余失败仅 3 条：`推荐个下饭剧呗`、`预算三千买什么手机好`、`合租好还是整租好`
（均为已补大类下的具体细分盲点）。

新增命中的质量抽查（贴题 + 人格一致 + 四要素完整）：
- `今天被放鸽子了` → "本喵从不放你鸽子喵"
- `我该不该辞职` → "先想清楚三件事：钱够不够撑三个月、下一家有没有着落、烦的是工作还是人"
- `要是我跟你吵架了你会先低头吗` → "……好吧，多半是本喵先，但你要配合着台阶下喵"

### 口径声明（必须看）

**T4 的提升含"同类泄露"性质**：60 条语料是按 T4 暴露的空洞类别定向编写的，
所以 95.6% 不能当作真实世界的泛化水平。它证明的是：

> **"发现盲点 → 定向补洞 → 泛化提升"这条方法论成立，且开销几乎为零**
> （60 条 = 点积 +0.2ms + 内存 +0.4MB）。

按补洞后口径估算加权可用率 ≈ 89%（T3 85% × 0.55 + T4 93% × 0.45），
**等效 ≈ 8B–14B**——但同样需声明：这是"考纲内"口径，真实分布会低于此。
真实水平的提升来自把补洞流程接入真实对话日志，持续迭代。

## 九、扩容到 2563 条 + npy 改造（v1.1 追加）

### 9.1 三类新语料

| 文件 | 条数 | 性质 |
|---|---|---|
| `mengyao_hq_part17_augment.jsonl` | 1734 | **query 增广**：每条 q 程序化生成 1–3 个自然变体（语气词/缩写），**复用原 reply 零质量风险**，实现"同意思多份随机化" |
| `mengyao_hq_part18_knowledge.jsonl` | 25 | **知识语料示范批**：生活健康常识，统一用"本喵听说/记得"弱断言口吻降低幻觉伤害 |
| `mengyao_hq_part19_generic.jsonl` | 12 | **万金油多份**：通用陪伴回复的多种说法（陪我/抱抱/睡不着/心情复杂等），供随机化组装 |

语料总量：792 → **2563 条**。

### 9.2 存储改造：JSON → npy（回应"SQL 还是 npy"）

**裁决：npy，不引入 SQL。**

| 方案 | 向量检索 | 启动加载（2563条） | 适用性 |
|---|---|---|---|
| **npy + 内存矩阵（已实施）** | numpy BLAS 点积 1.2ms | **228 ms** | 单进程只读索引，完美匹配 |
| JSON（旧） | 同上 | ~6–8 s（2563条时不可接受） | 仅千条以内 |
| SQL/sqlite-vec | 全表扫描或扩展插件 | 快 | **多进程写入/结构化查询才需要** |

两者不冲突：若未来做"用户输入回流"，可用 sqlite 管**语料生命周期**（审核队列/去重/版本），检索面仍走 npy。SQL 是管理面，npy 是服务面。

首次重建实测 19s（一次性），**二次启动 228 ms**（npy 路径）。JSON 旧缓存自动迁移并移除。

### 9.3 扩容后性能（开销锁死验证）

| | 793 条 | **2563 条** | 变化 |
|---|---|---|---|
| semantic respond | 15.2 ms | **15.7 ms** | **持平（+0.5ms）** |
| mock respond | 5 ms | 18.4 ms | ↑（BM25/2-gram 索引变大，可接受） |
| 启动（缓存） | 215 ms | 228 ms | 持平 |
| 磁盘（向量） | 3 MB | 10.5 MB | 线性 |

**结论实锤：语义检索路径下，语料扩容 ≈ 只占磁盘，不占性能。** mock 路径有线性开销但仍是毫秒级。

命中复测（2563 条）：T2 30/30、T3 55/56、T4 65/68 —— 与 793 条持平。
**诚实说明**：增广变体是"语气词/缩写"模式，对 T4 这类全新说法无增益（符合预期），它的价值在真实用户带语气词、缩写、懒人打字时的命中稳定性。知识语料命中验证通过（"感冒了要不要多喝热水"→ 弱断言回复）。

### 9.4 用户输入回流 = "越聊越顺"（调研结论）

**业界已验证，美团检索式对话就是标准答案**：`索引日更新机制`——对话日志回流 → 清洗 → 日更新索引；双索引结构（个性化历史 + 通用高频兜底）。

适合我们的半自动管线：

```
respond 检测到降级/低分 → 记录 (query, 上下文) 到 崩溃日志
  → 聚类去重（高频先补）
  → LLM 生成候选回复（人格卡 + few-shot 约束）
  → 质量门：四要素校验 + 口癖率 + 敏感词
  → 人工确认（或高置信自动通过）
  → 入 partN.jsonl → 定期重建索引（npy，228ms）
```

风险与对策：垃圾输入污染 → 审核门；人格漂移 → 四要素硬校验；隐私 → 本地数据不出机。

**实现成本极低**：引擎已有 `suggest_llm` / 低分信号，加一个崩溃日志记录器 + 日更脚本即可。这是"越聊越顺"的正确姿势——**每个盲点都是真实聊崩的句子，补一条赚一条**。

### 9.5 关于"10000 条 + 99.9%"的诚实结论

- **99.9% 覆盖数学上不可达**（开放集合 + 对数曲线），可验收口径应为"未见句命中 ≥85%（补洞口径）+ 常用意图全覆盖"。
- 当前 2563 条已含程序化增广的全部收益（变体模式有限）。**剩余 7000+ 条只能走 LLM 管线**（需 DeepSeek key）——手写每批 60 条不现实。
- **对数曲线下 2500→10000 的边际收益仅 +8~12pp（外推，不可尽信）**；而"真实日志补洞"补的每一条都是实际聊崩的盲点，性价比远高于盲生 10000 条。
- 建议：先落"回流管线"（成本半天），用真实聊崩数据驱动扩容，规模自然长到该到的地方。

## 十、检索质量消融：分带置信 / act 先验 / reranker（v1.2 追加）

### 10.1 三项改造

| 改造 | 内容 |
|---|---|
| 分带置信 | 语义高带（≥0.80）直接接受；中带（阈值~0.80）须 top1-top2 分差 ≥0.03 才接受，否则标记存疑。**同回复变体（query 增广共享 a_raw）豁免**——分差小是假存疑 |
| act 先验阈值 | question +0.04（收紧，宁交 LLM 不硬答）；empathy −0.04（放宽，接住情绪优先） |
| reranker 仲裁 | cross-encoder (bge-reranker-v2-m3 int8 ONNX, 880MB) 对 top-8 交互打分，仅存疑带触发，logit ≥ −1.5（sigmoid 0.18）才接受 |

### 10.2 reranker 选型标定（诚实记录两次失败/修正）

- **bge-reranker-base：域内完全失效**。自配正样本 median logit 1.20，OOD 负样本 median **1.47（比正样本还高）**，分布完全重叠，弃用。
- **v2-m3 第一版阈值 0.5（sigmoid）错杀**：用自配对（q=q）当正样本太简单（sig≥0.99）；真实 paraphrase 级命中 logit 分布宽（min −4.73, p5 −2.13, med 3.26）。改为真实命中对标定后取 **logit −1.5**：负样本（OOD top1, max −1.84）0 泄漏，正样本保留 ~92%。
- **v2-m3 onnx 加载修复**：社区量化版含 1 处非法 fp16 DequantizeLinear scale（opset 11），cast 为 fp32 + 修输出声明后正常加载（语义等价）。
- 标定数据：`rerank_calib_v2m3.json`（正 n=139 / 负 n=12）。

### 10.3 消融结果（`bench_ablation_v3.4.py`，T4 已按 2-gram≥0.6 语料外过滤）

| 配置 | T2 高频 | T3 改述 | T4 未见 | OOD 误命中 | 平均延迟 | rerank 触发 |
|---|---|---|---|---|---|---|
| A baseline（全关） | 55/56 | 30/30 | 56/58 | 0/12 | 13.7ms | 0 |
| B +分带 | 55/56 | 30/30 | 52/58 | 0/12 | 14.0ms | 0 |
| C +分带+act先验 | 55/56 | 30/30 | 51/58 | 0/12 | 14.0ms | 0 |
| **D 全开（+reranker）** | 55/56 | 30/30 | **55/58** | 0/12 | **13.7ms** | 4（≈2.6%） |

### 10.4 性价比结论

- **B/C 不能单独上线**：分带/收紧阈值砍掉的真命中没有 reranker 兜底，T4 净亏 4~5 条。
- **D vs A 的 T4 分歧只有 1 条**：「这个礼物送女生合适吗」——A 以 0.727 置信回复「这礼物最香喵」（答非所问的**假阳性**），D 拒绝并引导连 LLM（正确行为）。即 D 的 55 含金量 ≥ A 的 56。
- 延迟零成本：reranker 懒加载（启动不加载），触发率 2.6%，触发单次 +170ms（568M int8 CPU 的内存带宽墙，线程数调不动）。
- 成本：磁盘 +880MB；`is_available()` 为 False 时自动 fail-closed 回退 baseline 行为。
- **保留 D 配置为产品默认**。诚实局限：本测试集只有 1 个域内假阳性样本佐证 reranker 的收益，保护面（触发率 2.6%）窄，其价值定位是「串台保险」而非召回增强。

## 十一、拟人化改造：连贯性重排 + 复读硬排除（v1.3 追加）

背景：用户允许回复间隔放宽到 400ms，研究后放弃 LLM 改写与 seq2seq 生成路线（0.5B Q4 在 5060 级 GPU 改写 30-40 token ≈400-600ms 压线超预算，且有人格漂移/幻觉/破坏四要素三重风险；小 T5 中文改写质量为同义词机械替换）。400ms 预算全部花在「挑回复」而非「写回复」。

### 11.1 两项改造

| 改造 | 机制 |
|---|---|
| **L1.5 连贯性重排**（复用 v2-m3） | 仅多轮且候选回复互不同、best conf <0.90 时触发：cross-encoder 对 (上一轮 query, 回复正文) 打分重排 top-3 去重候选，治「检索只看本句、回复接不上上文」。max_len 56 |
| **复读硬排除** | 多样性候选池剔除最近 8 轮用过的 a_raw（剔除后仍有存活才生效）；配合候选池「相对窗∪绝对地板」：floor = max(min(best−0.10, 0.75), 0.65)——修复精确命中（best≈0.98）时相对窗把同意图候选全卡死的复读根源 |
| **候选面扩窗** | `_retrieve_scored` top-3→top-8，按 a_raw 去重后进池，多样性池从先天 ≤3 条扩到 ~5-8 条不同回复 |
| **神经预算共享** | 单轮内仲裁 rerank 与连贯性重排互斥（`_nn_spent` 记账），防串联叠加顶爆预算 |

### 11.2 三个性能坑（诚实记录）

1. **int8 前向成本被低估**：568M int8 的 DequantizeLinear 是内存带宽墙，5 对×96 token 实测 568ms（非线性外推可得）；砍到 3 对×56 token。
2. **线程池踩踏（最隐蔽）**：reranker session 默认 24 逻辑核全开，与 bge-m3 embed session 互相踩踏，单次 326~3900ms 剧烈抖动；锁 `intra_op_num_threads=8` 后稳定 ~150ms。**两个 ORT session 共存时必须都锁线程**。
3. **尖峰误判**：p95 里的 ~700ms 尖峰一半是环境噪声（首次推理/系统调度）和天气工具外网延迟，H2 指标改用中位数+p95 并剔除工具轮。

### 11.3 基准结果（`bench_humanlike_v3.5.py`，12 连问 × 8 意图 + 回归）

| 配置 | H1 复读去重 | H2 延迟中位 | H2 p95 | T5 多轮 | R1 回归 |
|---|---|---|---|---|---|
| OFF（无连贯/无去重） | 5.75~6.25/12 | 15.3ms | 17.0ms | 6/7 | T2 55/56 · T3 30/30 · T4 55/58 · OOD 0/12 |
| **ON（产品默认）** | **6.62/12** | **20.9ms** | **250.5ms** | 6/7 | 同 OFF，零回归 |

- H1 三轮复测 ON 均高于 OFF（+0.4~1.4 条不同回复/12 问），方向一致；绝对值受语料同意图回复数上限约束（「在干嘛」dense top-20 内仅 11 条不同回复）。
- 延迟：中位 20.9ms、p95 250ms，全部锁在 400ms 预算内；高置信轮（≥0.90）自动跳过重排回 ~15ms。
- 召回判定零回归：R1 与 T5 与改造前完全一致（选路改动不影响 recall_real 判定）。

### 11.4 结论

- **采纳**：连贯性重排 + 复读硬排除 + 候选扩窗 + 神经预算共享，全开为产品默认（FEATURES 五开关）。
- **放弃**（用户拍板）：LLM 改写路线、seq2seq 生成路线——留档不做。
- **后续可选**：H1 上限受语料同意图回复数约束，扩多样性最便宜的路仍是按意图补写不同回复（part19 模式），每条新回复直接进多样性池。
