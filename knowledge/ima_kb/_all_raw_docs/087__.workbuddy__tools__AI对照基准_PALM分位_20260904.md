# AI 生成项目对照基准：P.A.L.M 分位参考（轻量版，2026-09-04）

## 口径与方法
- 目的：给 P.A.L.M 的 codequal 分数一个"AI 项目群"参照系（前次结论缺对照样本）。
- 候选：GitHub 上**公开自述以 AI/vibe/agent 为主要编写方式**的中小 Python 仓库 5 个，浅层 zip 下载（无 .git 历史）。
- 同参扫描：`codequal.py <root> --dims all`（default profile，与 P.A.L.M 完全一致，含测试文件）。
- 局限（必须声明）：①"100% AI 编写"无法程序验证，按公开声明归类；②体量差 100 倍（205 行 ~ 74k 行），小语料天然低残留、分数偏乐观，只能看方向；③样本仅 5 个，非统计意义分位。

## 结论（方向性）
1. P.A.L.M **87.1 落在该小样本带中上（5 个里列第 3）**，且是全组唯一 74k 行语料——分数随规模增长自然下移，P.A.L.M 用 6-36 倍的代码量守住同档，实际好于表面名次。
2. **duplication 是 P.A.L.M 相对全组的唯一明显弱项**：dup% 15.16% 是全组最差（他人 0-8%），dup 维 64.9(C) 是组内唯一 C——对照组再次印证"消重 = 头号动作"，且这不是工具阈值偏心（同参可比）。
3. 死代码/命名按**行归一**其实干净：kubeauto 16 死imp/2.7k 行（0.6%），P.A.L.M 179/74k 行（0.24%）；命名违规组内 0-10，P.A.L.M 32 中过半是 do_GET 族 API 强制名。
4. 成熟 + 人工长期打磨的 gpt-engineer/clearmap 居首 → 说明**决定分数的更多是生成后的审校迭代纪律，而不是"是否 AI 写"**（与研究结论一致）。

## 附：这套工具做"防 AI 屎山"的用法（gate 化）
```
# 每批 AI 生成/合并前跑一次，低于门槛退出非零：
codequal.py <src> --exclude 'GPT-SoVITS|_legacy_tools' --dims all --fail-under 80 --json q.json
dynprobe.py --kind security --path <src> --fail-under 90
```
留证 JSON 进仓库 `.metrics/` 可做跨版本趋势：重复率/死代码数上升 = 屎山在累积，直接可归因到某次合并。
