# 框架设计：安全 · 权限 · 日志「三位一体底座」

> **定位**：这是**底层框架**的底座 —— 安全 / 权限 / 日志下沉到**最底层**、**不可绕过**。
> 上层建筑（业务、Agent、UI）一律建在它之上。
> 取材：P.A.L.M 自身设计（安全审计+红队报告、白皮书、演进史、独创报告）。
> 范围：框架层。**已剔除过度工程**（见 §6）。

---

## 0. 三条信条

1. **三位一体在底层**：安全 / 权限 / 日志 是**底座**，不是附加件；上层一切敏感动作必须经底座。
2. **fail-closed（默认拒绝）**：未配置 / 异常 / 解析为空 → **拒绝**，而非放行。
3. **缺失归一降级**：组件缺失 → 归一 `None`，业务判空，**不崩、不阻断**。

---

## 1. 三层（自下而上）

```
┌──────────────────────────────────────────────────────┐
│ L2 插件层   能力 = 插件（上层建筑在此构建）               │
├──────────────────────────────────────────────────────┤
│ L1 内核层   加载 · 卸载 · 依赖 · 生命周期                 │
│            服务容器（缺失归一 None）· 单一装配点 · 事件总线 │
├──────────────────────────────────────────────────────┤
│ L0 底座（不可绕过）  安全 · 权限 · 日志                    │
└──────────────────────────────────────────────────────┘
```

**铁律：L2 的一切敏感动作必须经 L0** —— 出网 / 命令 / 敏感路径 / 敏感能力 / 写操作 /
**模块间请求（带加密信息头）**，全部过底座（门面收敛）。绕不过去，才算"到底层"。

---

## 2. L0-安全（Security）

| 机制 | 做法 | 原则 |
|---|---|---|
| **唯一出网门面** | 所有出网经此一处；未配置 / 异常 → **拒绝** | fail-closed |
| **路径归一 + 敏感路径** | realpath 归一，拦 `..` / `\\?\` / `~`；`win.ini`/`system32`/`passwd` 等读写一律拦 | 归一化防绕过 |
| **命令守卫** | 危险指令黑名单（跨平台）+ 空白 / 斜杠归一 | 归一化防绕过 |
| **SSRF 基础防护** | 进制 IP 显式解析拒绝；解析为空即拒 | fail-closed |
| **注入清洗（单层）** | 输入清洗（注入短语变体）+ 外部内容剥离 | 够用即可 |
| **模块沙箱** | 每模块独立（见 `模块沙箱设计.md`） | 轻量 |
| **握手鉴权** | 见 §2.1 | 身份绑定 |

---

### 2.1 模块握手与请求鉴权（随机盐 + 主密钥 + 加密信息头）

> 你的原始设计：模块加载初始化时做随机盐加密；请求前缀带加密信息头，识别一致才接收；
> 主密钥随框架初始化随机生成；模块 init 读框架主密钥并自己生成随机盐发给框架；用对称加密便于统一解密。

1. **主密钥随框架初始化随机生成**：`MK = CSPRNG(32B)`，**仅存内存、不落盘**，重启即轮换。
2. **模块握手（加载时）**：模块读 MK → **自己生成随机盐** `S = CSPRNG(16B)`（每次加载重新随机）
   → 双方派生**对称会话密钥** `SK = KDF(MK, S)` → 模块把 `(moduleId, S)` 注册给内核。
3. **请求前缀 = 加密信息头**：`X-Mod-Auth: moduleId | saltId | nonce | AEAD(SK, nonce, payload/tag)`；
   接收方同法派生 `SK` 解密校验（含 nonce 防重放）→ **一致才接收，否则拒绝**。
4. **统一对称 AEAD**（AES-GCM / SM4-GCM）—— 便于统一解密，且自带完整性。

**与权限 / 日志咬合**：握手通过 → 身份确立 → 交**权限**判"准不准做"；握手 / 校验 / 拒绝 → 落**日志**。

**诚实标注**：模块能读 MK，所以这是**身份绑定 + 请求完整性 + 防重放**，**不是**防恶意模块的信任边界；
盐每次加载重新随机 → 模块重载后**旧请求头自动失效**。

## 3. L0-权限（Permission）

| 机制 | 做法 |
|---|---|
| **授权状态** | 敏感能力须用户授权；**未授权 → 拒绝**（fail-closed） |
| **持久化** | `permissions.json` 保存授权状态（跨会话） |
| **与安全分工** | **权限 = 准不准做**（授权状态，长期）；**安全 = 能不能做**（门面 / 防护，即时） |
| **审计联动** | 每次授权 / 拒绝 → 落日志 |

---

## 4. L0-日志（Log）

| 机制 | 做法 |
|---|---|
| **append-only 事件流** | 记录系统 / 模型看到的一切（提示、推理、调用与结果、注入、授权决策）→ **单一真相源** |
| **留痕** | 敏感能力调用留痕（滚动保留最近 N 条） |
| **不可篡改** | 只追加、不回改历史 |

> 前端"可视化"与后端"审计"消费的是**同一份事件流** —— 这就是"日志到底层"的价值。

---

## 5. 高可用（只留 3 条）

1. **缺失归一降级**：底座 / 插件缺失 → `None`，业务判空，**不崩**。
2. **可逆回滚**：热插拔卸载即回滚副作用（见沙箱 / 插件契约）。
3. **可重试**：限流 / 超时等可重试错误自动重试。

> 思路：**能降级就降级、能重试就重试、能回滚就回滚**，绝不因单点缺失整体崩。

---

## 6. 明确不做（剔除过度工程 / 上层建筑）

| 不做 | 原因 |
|---|---|
| 多档裁决引擎、规则热重载、看门狗、保险库 | 上层运维/治理，按需再加 |
| 纵深沙箱（AST+网络拦截+蜜罐）、信任根炸弹框架 | 过度设计；底层只要"稍微防" |
| 双总线、工具执行四件套、分级启动 | 过度抽象 |
| 沙箱多级隔离（受限执行 / 远端 tcp·ws） | 过度设计 |
