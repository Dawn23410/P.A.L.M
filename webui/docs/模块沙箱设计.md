# 模块沙箱设计（轻量 · 安全 · 低开销）

> **定位**：**底层框架**的模块隔离机制。核心原则 **轻量 / 安全 / 低开销**。
> 明确取舍：**不追求强隔离**，**"稍微防就行"** —— 默认进程内，重模块**可选**子进程。
> 范围：框架层。**已剔除过度工程**（不搞多级隔离 / 远端传输 / 蜜罐）。

---

## 0. 三条底线（"稍微防"到底防什么）

1. **模块不能碰全局**（不污染、不直连外部 IO）
2. **模块不能碰别的模块**（跨模块只能走服务，且过护栏）
3. **模块崩不能拖垮系统**（故障关在自己边界内）

> 即：防**误伤 / 越界 / 崩溃扩散**；**不防**恶意模块。

---

## 1. 核心模型：能力对象注入 + 作用域隔离

```
内核 ──生成 ctx（该模块专属能力对象）──▶ 模块（独立作用域）
模块只能通过 ctx 访问外部；ctx 上没有的 = 访问不到
```

- 每个模块 = **一个独立作用域** + **一份专属 `ctx`**。
- `ctx` 上没有的能力，**根本没有**（不是"报错后放行"）。
- 前后端同构：**JS** 用 ES module scope + `ctx`（不给 window/fetch 直连）；**Python** 用命名空间 + `ctx`（不直接 import os/subprocess）。

---

## 2. 三道轻量护栏

| # | 护栏 | 做法 | 开销 |
|---|---|---|---|
| 1 | **作用域隔离** | 模块跑在自己的 scope，无共享可变全局 | ≈0 |
| 2 | **能力白名单** | `ctx` 只挂**被授权**的能力 | ≈0 |
| 3 | **故障边界** | 生命周期 + 每次调用 `try/catch` + 超时；崩只标记 `degraded` | ≈0 |

**咬合点**：`ctx` 的能力经**一层薄包装**，调用时顺带完成
「握手校验 → 权限判定 → 日志留痕」——**沙箱不另造一套，直接复用底座**（成本：一次函数包装）。

---

## 3. 隔离强度：只留 2 档

| 档 | 形态 | 开销 | 适用 | 默认 |
|---|---|---|---|---|
| **进程内** | 作用域 + 能力注入 + 护栏 | **≈0** | 绝大多数模块 | ✅ |
| **子进程** | 独立进程 | 中 | 重计算 / 高风险模块（按声明启用） | 声明启用 |

- **默认永远进程内**；子进程由**模块声明**决定，**不声明就不升级**（缺失归一，绝不因缺配置启动失败）。
- 不搞"受限执行 / 远端传输 / 多级隔离"——那是过度工程。

---

## 4. 开销账（为什么敢叫"低开销"）

| 环节 | 成本 |
|---|---|
| 作用域隔离 | ES module / Python namespace → **免费** |
| 能力注入 | 构造一个对象 → **免费** |
| 薄包装（咬合点） | 每次调用一层函数包装 → **纳秒级** |
| 故障边界 | `try/catch` → **近免费** |
| **合计（进程内）** | **正常模块开销 ≈ 0** |

> 只有子进程档才有真开销 → 所以**默认不升级**。

---

## 5. 诚实标注

- **这不是安全边界**：进程内模块仍能拿到 `ctx` 里的能力，也**能读到主密钥**。
- 能防：**误伤全局 / 越界访问 / 崩溃扩散 / 未授权能力调用**。
- 防不了：恶意模块、内存窥探、原生扩展越权。
- 要真边界 → 升级**子进程**档。
