# 自研 LLM 内核 vs 开源实现：控制变量对照实验 v1.0

> 目的：回答「本内核那层薄封装到底花了多少钱」，并给出**与主流开源实现同条件对比**的数字。
> 
> **结论先行**：本内核净开销 ≈ **+0.83 ms/次**，是本轮同语言四个实现里最轻的一个；LiteLLM +18.72 ms、OpenAI SDK +5.85 ms。
> 两个自托管网关（跨语言，单独成组、不与内核并列排名）分别约 +2.73 ms 与 +30.45 ms。
> 但最该记住的是另一条：**当模型延迟真的存在（约 477 ms）时，除 Portkey（+3.79 ms）外的差异全被淹没**。

---

## 一、实验设计（控制变量）

所有被测实现**指向同一个本地确定性 mock 上游**，测量的是纯粹的「客户端/网关这一层」
开销，不含任何供应商侧变量：

```
被测实现 ──HTTP/1.1 keep-alive──> mock 上游（服务端固定约 0.5 ms，可注入固定延迟）
```

- **净开销 = 该实现的 mean − 直连 httpx 的 mean**（同机、同回环、同进程模型）
- 一次调用 = **把整条 SSE 流读完**（含收尾帧）的墙钟；不是首字节、不是「发出即返回」
- 并发 = 1（顺序单发）：网关差异本就在毫秒级，并发排队噪声会把信号埋掉
- 每轮先热身 50 次（不计入）；每次测量前 reset mock 侧计数
- **基线复测**：整轮跑完再测一次基线，用两次之差作为本机**可复现性下限**；
  小于它的净开销一律标注「噪声级」，不编故事

### 为什么不用真实厂商端点

真实模型延迟 0.5–5 s、网络与供应商负载都在动，网关那几毫秒的差异**看不见也复现不了**。
把上游钉死成「固定延迟的本地进程」，才能把「网关」这一个变量单独解出来。
代价是绝对数偏离生产 —— 见第七节。

### 一个必须先修掉的伪像：Nagle + 延迟 ACK 的 40 ms

首版 mock 没关 Nagle，基线直接测出 **44 ms**，而 mock 侧自报只花 0.6 ms。
原因是流式响应「一个 chunk 一次小写」：发送端 Nagle 在等对端 ACK，对端的延迟 ACK 是 40 ms，
两条规则凑一起就是每请求凭空 +40 ms —— 足以把网关差异整个盖住。
修法：mock 侧 `TCP_NODELAY` + 每个 chunk 立即 flush。修后基线 2.6 ms，量级才对。
**这是本次实验最重要的工程发现**，已写进 `mock_upstream.py` 的注释里。

## 三、第一轮：零延迟（只量「那一层」的成本）

`--ack-delay-ms 0 --chunk-delay-ms 0 --completion-tokens 16`，500 次/实现，热身 50 次。

| 实现 | wall mean | Δ 净开销 | p50 | p90 | p99 | stdev | n | 错误 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 直连 httpx（基线） | 2.944 ms | +0.008 ms | 2.808 | 3.640 | 5.034 | 0.575 | 500 | 0 |
| **P.A.L.M 内核**（本仓库） | 3.770 ms | +0.834 ms | 3.570 | 4.708 | 5.952 | 0.840 | 500 | 0 |
| LiteLLM（Python） | 21.656 ms | +18.720 ms | 21.511 | 24.035 | 25.474 | 1.819 | 500 | 0 |
| OpenAI 官方 SDK | 8.787 ms | +5.851 ms | 8.423 | 10.479 | 12.802 | 1.288 | 500 | 0 |
| Bifrost（Go，自托管） | 5.670 ms | +2.734 ms | 5.454 | 6.851 | 9.112 | 0.984 | 500 | 0 |
| Portkey Gateway（Node，自托管） | 33.382 ms | +30.445 ms | 33.241 | 34.516 | 36.655 | 1.017 | 500 | 0 |
| 直连 httpx（复测） | 2.929 ms | -0.007 ms | 2.796 | 3.645 | 4.695 | 0.543 | 500 | 0 |

基线口径：首轮 `2.944 ms` 与复测 `2.929 ms` 的均值 = **2.936 ms**；**漂移带 ±0.015 ms**（同一份代码跑两次的差，即本机可复现性下限）。

### TTFT（首个正文帧）

| 实现 | TTFT mean | TTFT p50 | TTFT p90 | 相对基线 |
|---|---:|---:|---:|---:|
| 直连 httpx（基线） | 2.012 ms | 1.915 | 2.468 | +0.000 ms |
| **P.A.L.M 内核**（本仓库） | 2.445 ms | 2.275 | 3.046 | +0.433 ms |
| LiteLLM（Python） | 10.103 ms | 9.833 | 11.596 | +8.091 ms |
| OpenAI 官方 SDK | 4.218 ms | 3.997 | 5.120 | +2.206 ms |

**读法**：`palm_kernel` 的 Δ = **+0.83 ms**，高于漂移带（±0.015 ms），可以认为是个真实但极小的开销。对比之下 LiteLLM +18.72 ms、Portkey +30.45 ms 是稳定且远超噪声的开销。

| LiteLLM（Python） | 485.579 ms | +9.477 ms | 485.862 | 487.964 | 488.913 | 2.228 | 80 | 0 |

| 实现 | TTFT mean | TTFT p50 | TTFT p90 | 相对基线 |
|---|---:|---:|---:|---:|
| 直连 httpx（基线） | 308.641 ms | 308.358 | 309.761 | +0.000 ms |
| **P.A.L.M 内核**（本仓库） | 308.753 ms | 308.612 | 309.696 | +0.112 ms |
| LiteLLM（Python） | 314.356 ms | 314.288 | 315.827 | +5.715 ms |
| OpenAI 官方 SDK | 310.113 ms | 310.076 | 311.061 | +1.472 ms |

**读法**：总耗时全部落在同一区间，除 Portkey（+3.79 ms）外**没有任何实现的差异超过噪声带**。
但 TTFT 一列仍有信号：Portkey 的 +24.3 ms 首字惩罚在总时长被淹没后**依然可见**。
这就是「该看哪个指标」的经验：**网关的开销主要落在首字节**，总时长由模型解码主导。

## 五、分组与可比性声明

| 组 | 成员 | 可比性 |
|---|---|---|
| **同语言正面对照组** | 直连 httpx / **本内核** / LiteLLM / OpenAI SDK | 可比：同为 Python 进程内库，同解释器、同进程模型 |
| **跨语言参照组** | Bifrost（Go）/ Portkey（Node，Docker `--network host`） | **不可直接比**：各多一次真实网络跳、独立运行时与进程；只作量级参照 |

跨语言两组与同语言组共用同一个 mock、同一台机器，但「多一跳」本身就值几毫秒，
所以本报告**从不把它们与内核并列排名**，只在同组内互相比较
（Bifrost vs Portkey 可比 —— 两者容器化方式与网络路径一致）。

## 六、与第三方公开数字对照

本实验之外，公开可查的第三方基准（口径见各自原文，此处仅作量级参照，**不与本表逐项对号**）：

| 实现 | 第三方报告的额外开销（mean） | 来源口径 |
|---|---|---|
| LiteLLM（Python） | 约 5.8 ms（早期版本曾测到 87–258 ms） | BerriAI 自家 `AIGatewayBench`（指向同一 mock 上游，净开销 = 经过网关 − 直连） |
| Bifrost（Go） | 0.62–4.5 ms | 同上（Bifrost 在该基准中为最低一档） |
| Portkey Gateway | 2.65–27.6 ms | 同上 |

对本表的三点提示：

1. **量级一致，绝对值不必一致**。本实验 LiteLLM +18.7 ms、Portkey +30.4 ms、Bifrost +2.7 ms，
   与第三方区间重叠或同量级；LiteLLM 偏高可解释为版本差异（本次 1.102.0，带完整成本表与
   回退逻辑）。**跨机器、跨版本的数字本就不该逐位相等。**
2. **第三方同样强调「相对真实模型延迟不可见」**。该基准自己也写明：真实模型延迟 500 ms–5 s 时，
   网关之间的差异往往不可观测 —— 与本报告第四节的实测完全吻合。
3. **不要用本表否定这些网关**。它们的主体价值（多供应商路由、熔断、缓存、密钥与配额治理、
   可观测性）不在本次测量范围内；本实验只回答了「多这层代理要花多少延迟」。

## 七、局限与伪像（必须一起读）

1. **回环不是网络**。同机回环没有 RTT、没有丢包重传、没有跨区路由。真实链路上网关的
   每一跳都更贵，本表的净开销是**下界**。
2. **没有 TLS**。真实网关要终结 HTTPS，握手与加解密成本未计入（连接复用时影响小，但不为零）。
3. **并发 = 1**。排队 / 限流 / 背压恰恰是网关的核心价值之一，本实验刻意把并发拿掉以保信号纯度，
   因此**不能**从本表推断高并发表现。
4. **mock 是单线程模型**（每请求一线程），但它本身不是被测对象；其 0.5 ms 服务端耗时已单列，可自行扣除。
5. **容器用 host 网络**。Bifrost/Portkey 以 `--network host` 运行以消除端口映射噪声，
   与生产部署形态不同，但对两者是同等处理。
6. **顺序效应已量化但仍存在**。各实现按固定顺序跑，基线复测给出漂移带；因此
   「内核 +0.83 ms」只说明开销**很小**，不主张精确到小数第三位。
7. **这不是功能对比**。本实验只量延迟开销，不评价路由 / 熔断 / 缓存 / 密钥治理等能力 ——
   那些才是这些网关的主体价值，而本内核**并不打算**做那些事。
8. **配置形态可能影响结果**。Bifrost 用 management API 注册上游、Portkey 用请求头路由，
   均为各自文档的推荐姿势，但与你的生产配置不同时开销会变。

## 八、结论

1. **这层封装足够薄**：净开销 +0.83 ms/次（LiteLLM +18.72 ms、OpenAI SDK +5.85 ms），同语言四个实现里最轻。
   与设计意图一致 —— 内核不做重试编排 / 虚拟密钥 / 负载均衡，只做协议归一与参数卫生。
2. **轻不等于没成本，而是成本花在别处**：内核的收益在协议覆盖（四种原生通道）、
   参数卫生（禁参剔除 / 档位夹取）、能力矩阵前置拦截、文本工具降级这些**正确性**上。
   这次实验说明它没有为这些正确性付明显的延迟代价。
3. **延迟要看 TTFT，不是总时长**：拟真配置下总时长差异全部淹没，只有 TTFT 还留着信号。
4. **网关选型不能只看这几毫秒**：Portkey 的 +30.45 ms 在 477 ms 的回合里
   只占约 6.4%。如果它换来的可观测性与密钥治理值这个价，它就是对的 —— 数字要放进场景里读。

## 九、复现

```bash
# 依赖：WSL2 Ubuntu 22.04 + Docker（Bifrost/Portkey 需要）
#       venv 内 httpx / pydantic / litellm / openai
cd bench/gateway

# 第一轮：零延迟（纯开销）
RESDIR=results_zero bash run_bench.sh 500 50

# 第二轮：拟真延迟
RESDIR=results_load ACK_MS=300 CHUNK_MS=5 MAXTOK=32 bash run_bench.sh 80 10

# 出报告
python3 report.py --zero results_zero --load results_load \
    --out ../../docs/网关对照实验_v1.0.md
```

文件清单：`mock_upstream.py`（确定性上游）、`clients.py`（四类客户端）、
`harness.py`（计时器）、`run_bench.sh`（编排）、`report.py`（本报告生成）、
`results_zero/` 与 `results_load/`（原始样本，逐次耗时全部保留）。
