# 回传拆分器字段说明 v1.0

> **API 面已统一（2026-09-23）**：对外入口收敛为 `palm_llm`（等价 `palm_llm.api`），
> 内部实现件全部加下划线私有。下文若出现旧函数名/旧模块路径，那是当时的形态；
> **当前清单与改名对照见 [《API函数库重构_v1.0》](API函数库重构_v1.0.md)。**

> 落码位置：`palm_llm/providers/_telemetry.py`
> 用例：`tests/test_telemetry.py`
> 挂载点：三个 provider 的 `done` 帧 → `{"done": true, "usage": {...}, "stats": {...}}`

## 一、它解决什么

"把回传拆开"要同时做两件事，只做一件都会得到**错的数**：

1. **字段名归一** —— 同一件事各家名字不同（缓存命中就有 4 种叫法）。
2. **口径归一** —— 同名不等于同义。**最典型的一个**：

   - OpenAI 系 `prompt_tokens` **含**缓存命中；
   - Anthropic `input_tokens` **不含**缓存命中。

   若只做字段名映射，同一份缓存命中量在两家会算出两个总输入。

本模块统一为：

```
input_tokens        非缓存输入
cache_read_tokens   缓存命中（读）
cache_write_tokens  缓存写入
total_tokens = input + cache_read + cache_write + output
```

## 二、字段字典

### 元信息

| 字段 | 单位 | 说明 |
|---|---|---|
| `model` | — | 调用时**请求**的模型名（不是服务端回传的那个） |
| `response_id` | — | 服务端响应 id（OpenAI `id` / Anthropic `message.id`）；放 `extra` |
| `finish_reason` | — | 已归一为 OpenAI 口径：`stop` / `length` / `tool_calls` / `content_filter` / `pause` |
| `stop_sequence` | — | 命中的自定义停止串（Anthropic 原生才有） |

### 内容

| 字段 | 说明 |
|---|---|
| `reasoning_text` | 思考全文（累积） |
| `content_text` | 正文全文（累积） |

> 流式消费方本就能从事件流拿到这两个；这里再给一份是为了**非流式消费方一次取用**，
> 以及"落库 / 归档时不必自己拼"。

### token 计数

| 字段 | 各家来源 |
|---|---|
| `input_tokens` | OpenAI `prompt_tokens` − 缓存；DeepSeek `prompt_cache_miss_tokens`；Anthropic `input_tokens` |
| `cache_read_tokens` | OpenAI `prompt_tokens_details.cached_tokens`；DeepSeek `prompt_cache_hit_tokens`；Anthropic `cache_read_input_tokens` |
| `cache_write_tokens` | Anthropic `cache_creation_input_tokens`；OpenAI 系 `cache_creation_input_tokens` / `prompt_cache_write_tokens` |
| `output_tokens` | 三家同名 |
| `reasoning_tokens` | OpenAI `completion_tokens_details.reasoning_tokens`；**Anthropic 不单列 → 恒为 0** |
| `total_tokens` | 按上面公式重算（不直接采信厂商的 total） |

> `reasoning_tokens` 在 Anthropic 上留 0 是**刻意的**：接口不单列就是不可知，
> 用"输出 − 正文估算"去补会得到一个看起来精确的假数。

### 计时

| 字段 | 单位 | 起点 → 终点 | 为什么单独拆出来 |
|---|---|---|---|
| `ttack_ms` | ms | 请求发出 → HTTP 响应头到达 | 把**网络/排队/路由**与推理本身分开。网关抖动时这一项先飙 |
| `ttft_ms` | ms | 请求发出 → 第一个输出帧（含思考帧） | 业界标准口径 |
| `ttfa_ms` | ms | 请求发出 → 第一个**正文**帧 | 思考模型上 TTFT 会被思考时间完全掩盖，不拆就没有"用户真正看到字"的指标 |
| `thinking_ms` | ms | `ttfa_ms − ttft_ms` | 纯思考耗时 |
| `total_ms` | ms | 请求发出 → 流结束（端到端） | 同上 |
| `prefill_ms` | ms | 引擎侧提示预填充耗时 | 仅本地引擎（ollama）给；云端无此数 |
| `decode_ms` | ms | 引擎侧解码耗时 | 同上；有它时 `tps` 用它算（排除排队与网络） |
| `chunks` | 个 | 输出帧数 | 帧数**不等于** token 数（思考内容成块下发），只用于判断"流是否细粒度" |

### 派生

| 字段 | 算式 | 口径说明 |
|---|---|---|
| `tpot_ms` | `(total_ms − ttft_ms) / (output_tokens − 1)` | 每输出 token 平均耗时（Time Per Output Token） |
| `ntpot_ms` | `total_ms / output_tokens` | 按输出 token 数归一的请求延迟 |
| `itl_p50_ms` / `itl_p90_ms` | 相邻输出帧间隔的 50 / 90 分位 | 取分位而非均值：个别卡顿会把均值拉偏。**注意口径**：云端思考内容成块下发，此时它反映"到帧节奏"；本地 ollama 才是逐 token |
| `tps` | `output_tokens / decode_ms × 1000` | 解码速度。有引擎侧 `decode_ms` 就用它，否则用 `total_ms − ttft_ms` |
| `tps_total` | `output_tokens / total_ms × 1000` | 端到端速度（含排队、预填充、思考） |
| `cache_hit_rate` | `cache_read / (input + cache_read)` | 只看**输入侧**的命中率；不含缓存写入 |

### 厂商专有

| 字段 | 来源 |
|---|---|
| `extra.load_ms` | ollama：模型加载耗时 |
| `extra.prompt_eval_ms` / `extra.eval_ms` | ollama：预填充 / 解码 |
| `extra.engine_total_ms` | ollama：引擎自计总耗时 |
| `extra.thinking_signature` | Anthropic：思考块签名（见下） |
| `extra.response_id`、`extra.model` | 服务端回传的响应 id 与**实际**模型名 |

## 三、三个容易踩的口径坑

1. **`tps` 与 `tps_total` 不是一回事**。本地实测同一轮请求：`tps = 83.5`、`tps_total = 79.4`；
   而短回复排队占比高时差距更大（`tps = 87.7` vs `tps_total = 18.8`，差 4.7 倍）——
   因为后者把 425 ms 的排队/加载也算进了分母。**报速度必须说明是哪一个。**
2. **`itl` 在思考阶段无意义**。思考模型一次给几百字，帧间隔约等于"批量下发周期"，
   不是逐 token 延迟。要判"卡不卡"，看正文帧的 ITL。
3. **`reasoning_tokens` 缺失 ≠ 没有思考**。Anthropic 不单列；拿 `output_tokens − 正文长度`
   倒推会低估（思考与正文字符/token 比不同），所以留 0。

## 四、思考签名为什么留在 `extra` 里

Anthropic 的思考块带 `signature`，多轮对话必须**原样、原顺序**回传，改一个字节即 400。
故 `extra` 里存了两样东西：

- `thinking_signature`：所有签名按顺序拼成的一条字符串（人可读、便于排查）；
- `native_blocks`：**助手消息 content 数组的完整重建**（thinking / text / tool_use /
  redacted_thinking，含顺序），是真正拿去回传的凭据。

为什么不是只存思考块：思考块必须打头，交错思考（interleaved thinking）下还会夹在多个
`tool_use` 之间 —— 只存思考块就丢了位置，而"原顺序"正是 400 的判定线。

消费路径：`server.chat` 把它落到 `Message.reasoning_echo`，下一轮 `_replay` 带回内核，
Anthropic 通道发现凭据就整条复活（**且仅在本轮带 `tools` 时**——不带工具的轮次回传历史
思考会让它在 keep-all 模型上持续计入输入 token）。

契约分级、官方出处与安全默认值见 `docs/思考块回传契约_v1.0.md`。
