## 一、要解决的问题

`Profile.supports_vision` / `doc_mimes` / `max_file_mb` 这几个字段在 v1.4 之前**只是数据**：
填了值，但内核从不去读。于是：

- 把图片发给一个纯文本模型 → 白跑一次往返，拿回一个模糊的 400；
- 把一个 300 MB 的 PDF 塞进请求 → 服务端拒了才知道；
- 把 `application/msword` 发给只吃 PDF 的 Anthropic → 同上。

判断这些**根本不需要发请求**：内核手上就有 `Profile` / `ModelRule`。
本次落码把它接成一条**发请求前的闸门**。

---

## 二、三条设计铁律（决定了它长什么样）

### 铁律 1：只拦「已知不支持」

能力矩阵是抓来的，有覆盖盲区。`generic` 档位（本机 ollama 走这条）**连模型名都不固定** ——
你 `ollama pull` 了 `llava` 还是 `qwen2.5:0.5b`，内核无从得知。
在这种档位上按 `supports_vision=False` 硬拦，会把合法的多模态用法直接打死。

因此 `Profile.capabilities_known`：

| 档位 | 值 | 行为 |
|---|---|---|
| 10 家已知厂商 Profile | `True` | 违规**抛错** |
| `GENERIC`（含 ollama / 未知域名） | `False` | 一律**放行**，并返回一条 `capability_unknown` 记账，写进 `stats.extra` |

**宁可放过，不可错杀。** 需要严格预检的调用方改用 `capabilities_for()` 自行决策。

### 铁律 2：只看 `Message`，不看 payload

payload 是各家组装后的产物，形态已经漂移（OpenAI 是 content blocks、Anthropic 是
`document` 块、Gemini 是 `parts[].inlineData`）。校验若挂在 payload 上，
就会随协议实现变化而漏检。入参面是统一的，校验必须挂在那一层。

### 铁律 3：报错要能照着改

只说 `unsupported` 等于没说。每条错误都给出：**第几条消息** + **什么类型/多大** +
**支持什么** + **该怎么办** + **命中了哪条规则**。例：

```
[deepseek] 模型 deepseek-v4-pro 不支持视觉输入：第 2 条消息共带 1 张图
（能力档 deepseek），命中规则 'deepseek-(v4-pro|reasoner).*'。
处理：改用支持视觉的模型，或移除这些消息的 images。
```

## 三、接口与数据流

```
调用方 ── Message(images / files) ──┐
                                    ├─> check_capabilities(messages, profile, model, provider, rule)
Profile（已二级合并）+ ModelRule ───┘        │
                                             ├─ 违规 → raise CapabilityError（零网络往返）
                                             └─ 合规 → 返回 notes（并入 stats.extra）
```

| 名称 | 用途 |
|---|---|
| `CapabilityError(RuntimeError)` | 违规异常。继承 `RuntimeError` 与内核既有失败语义一致 |
| `check_capabilities(...) -> dict` | 闸门本体。四个 provider 的 `complete()` 入口各调一次 |
| `capabilities_for(base_url, type, model) -> dict` | 查询接口。给调用方预检 / UI 提示用，**不抛错** |

四个通道的接入点：`openai_compat.complete()`（profile 解析后）、`anthropic._build_payload()`、
`gemini._build_payload()`、`ollama.complete()`。加上 ollama 是因为它**同样会收到 images**。

## 四、检查项

| # | 检查 | 触发条件 | 结果 |
|---|---|---|---|
| 1 | 视觉 | `images` 非空且 `supports_vision=False` | 抛错 |
| 2 | 文档整体拒收 | `files` 非空且 `reject_documents=True` | 抛错（提示走各家的独立上传/解析通道） |
| 3 | 文档类型 | `files` 里的 mime 不在 `doc_mimes` 白名单 | 抛错（列出白名单） |
| 4 | 单文件体积 | 单文件 > `max_file_mb` | 抛错 |
| 5 | 合计体积 | 全部文档合计 > `max_file_mb` | 抛错（官方口径里单文件与单请求是两条限制） |
| 6 | 图片混进 `files` | `files` 里某条 mime 是 `image/*` | **转交视觉闸门**，不给它报「不支持文档」 |
| 7 | 类型/大小未知 | 远程 URL 未带 mime，或 dict 未给 size | **不猜、不拦**，记 `capability_size_unchecked` |

说明两处细节：

- **检查 6** 是真实踩出来的：`files` 里混进图片是常态（调用方不区分两个字段），
  若先跑「整体拒收」，一张图会收到「不支持文档输入」的错，误导排查方向。
- **体积按 base64 文本长度反推**（`len*3/4`，扣填充符），不真解码 —— 是近似值，
  但用于「超没超 50 MB」这一量级足够，且省掉一次全量解码。

## 五、规则数据复审（v2.0 §11 七项 + 能力字段补齐）

### 5.1 复审口径

**模型下线 / 改名一律「保留规则 + 补 note」，不删规则**。删掉会让仍在用旧名的调用方
匹配失败（回落 Profile 默认）；而「它下线了」这件事应该留在数据里。

### 5.2 逐项处置

| 项 | 原状 | 处置 | 依据 |
|---|---|---|---|
| DeepSeek 模型名 | 只认 `deepseek-v4-flash` | 正则改为 `deepseek-(v4-flash\|flash)`，**旧名保留** | v2.0 §6：`deepseek-flash` 是 V4.1-Flash 承接 |
| `deepseek-reasoner` | 规则在，note 只说「已退役」 | 补弃用日期 `2026-07-24`，说明规则保留原因 | v2.0 §6 |
| Kimi k2.5 | 规则在 | 补 `2026-08-31 下线`，说明保留原因 | v2.0 §7 |
| Claude `opus-4-5` | 规则在 | 补「已不在在售阵容表，保留为老账号」 | v2.0 §2 |
| Doubao 思考档位 | 只有 `seed-character` 不支持思考 | **新增 Seed 2.1 规则**：`reasoning_effort` 七档 | v2.0 §8 |
| Anthropic 档位 | 只有 adaptive + 禁 budget | 两条 adaptive 规则补 `effort_allowed=(low…max)` | v2.0 §2：`output_config.effort` |
| Qwen omni-turbo | note 写「不支持 enable_thinking」 | 补「模型名已不在当前文档，规则仅为兼容」 | v2.0 §5 |

### 5.3 能力字段补齐（本轮新增，直接喂给闸门）

| 供应商 | 改动 | 依据 |
|---|---|---|
| **OpenAI** | `doc_mimes` 由 `(pdf, text/plain, text/markdown)` **收窄为 `(application/pdf,)`** | 官方文件输入页：Chat Completions **只支持 `.pdf`**，其余格式属 Responses API 的 `input_file` |
| **Anthropic** | `max_file_mb` 保持 32，补注释说明为何不取 500 | 500 MB 是 **Files API** 口径；内联 base64 受请求体积限制，取 32 才是真闸门 |
| **DeepSeek** | 整家 `reject_documents=True`；`supports_vision` 默认 False，**仅 flash 放开** | v2.0 §6：明确不支持文档；V4-Pro 输入仅文本 |
| **Kimi** | `supports_vision=True`，整家 `reject_documents=True` | v2.0 §7：k3/k2.7/k2.6 含图与视频；文档走 `file-extract` 独立通道 |
| **Qwen** | 整家 `reject_documents=True`；删掉来路不明的 `max_file_mb=20` | v2.0 §5：原生只吃文本/图片/视频，文档走两条独立通道 |
| **Gemini** | `doc_mimes` 补 `text/plain` | v2.0 §3：文档类型为 `application/pdf` 与 `text/plain` |
| **GLM** | 拆出 `glm-5.3-flash`（多模态+文件）与 `glm-5.3`（**纯文本**）；4.5–5.x 文本系列一律 `supports_vision=False` + `reject_documents=True` | v2.0 §4：只有 flash 支持文件；「文本模型不原生吃文档，须经独立解析服务」 |
| **Hunyuan** | `reject_documents=True` | v2.0 §9：文档走**独立的文件上传 API**，不在对话请求里内联 |
| **Doubao** | 不设文档闸门 | v2.0 §8：「文档理解」仅标 Supported，扩展名/上限**未查到** → 不知道就不拦 |

> 最后一条是刻意的：**未查到的字段留空 = 不拦**。凭印象填一个数字，
> 比不填危险得多 —— 它会静默拦掉合法请求。

`tests/test_capability.py` 27 例，覆盖：

| 组 | 例数 | 关键断言 |
|---|---|---|
| 视觉闸门 | 5 | 纯文本模型带图抛错；**报错含「第 N 条消息」**；未知档位不拦且记 `capability_unknown` |
| 文档闸门 | 8 | 整家拒收；GLM 文本拒/Flash 放；白名单外 mime 抛错且**列出可用类型**；单文件超限；合计超限；图片混入 `files` 走视觉闸门；远程 URL 不猜 |
| 查询接口 | 5 | 矩阵查询；未知档位标记；**OpenAI 白名单必须是 PDF-only**；**改名/下线的旧名仍能解析** |

| 多模态渲染 | 5 | OpenAI `file` 块形状 / 缺 name 时按 mime 反推文件名 / Anthropic `document` 块 / `Message.to_openai` 不带空文本块 |

## 七、局限（必须一起读）

1. **闸门是静态判断，不是服务端权威**。厂商会静默改限制；放行 ≠ 服务端一定接受，
   拦下 ≠ 服务端一定拒绝。它的价值是「省一次往返 + 把模糊 400 换成可读错误」，
   **不能替代**对服务端错误的分支处理。
2. **数据面有洞**（已在 v1.5 §8 列出）：Doubao / Kimi / GLM-Flash 的体积上限未查到，
   MiniMax 与 xAI 未建 Profile。这些都按「未查到 = 不拦」处理，不是漏做。
3. **体积是近似值**：base64 反推有 <1% 误差，且远程 URL 完全算不出。
4. **只覆盖 `Message` 上的附件**。调用方若把文件内容塞进 `content` 文本（例如自己抽好文本），
   闸门无从判断 —— 那属于上游职责。
5. **`supports_vision` 的粒度是模型级**，而厂商的「同一模型不同版本/不同入口能力不同」
   （如同一模型的 Files API 与内联能力不同）不在数据里。
