# 工具（原生 Tool / Function Calling）专项审计

> 版本 v1.0 ｜ 2026-09-23 ｜ 来源：**逐文件实读 + 实机 payload 取证 + 厂商官方规格**
> 范围：`palm_llm` 三条通道的**声明 / 选择 / 回传 / 结果回填**四个环节

## 零、结论先行

三条通道的**请求方向**（工具声明、工具选择映射）与**响应方向**（分片拼装、完整下发）
都已通、都有用例。问题集中在**回填与边角契约**上，共 5 条，其中 2 条是 bug：

| # | 严重度 | 通道 | 问题 |
|---|---|---|---|
| F1 | 🔴 bug | ollama | 工具结果回填字段名用错（OpenAI 的 `name`/`tool_call_id` ≠ ollama 的 `tool_name`） |
| F2 | 🟡 bug | openai_compat | 非流式 `tool_calls` 未归一（缺 `index`，与流式路径形状不一致） |
| F3 | 🟡 契约冲突 | anthropic | 强制工具选择 × 手工思考同时下发 → 必然 400 |
| F4 | ⚪ 无据下发 | ollama | 下发了原生规格里不存在的 `tool_choice` |
| F5 | ⚪ 能力缺口 | 全部 | `is_error` / `parallel_tool_calls` / `strict` 无处表达 |

## 一、各通道现状盘点

| 环节 | openai_compat | anthropic | ollama |

## 二、F1：ollama 工具结果回填字段名用错（🔴）

内核 `Message.to_openai()` 产出的是 **OpenAI 形态**：

```json
{"role": "tool", "content": "11 度", "tool_call_id": "call_1", "name": "get_weather"}
```

而 ollama `/api/chat` 的消息对象**只认 `tool_name`，且没有 `tool_call_id`**（官方 api.md：
message 字段为 `role` / `content` / `thinking` / `images` / `tool_calls` / `tool_name`）。

**后果**：`tool_name` 缺失 → 模型收不到"哪个工具返回了什么"，多轮工具闭环在 ollama 通道上
是**断的**；`tool_call_id` 是未知字段，被忽略。
**为什么没被测出来**：`tests/test_ollama_provider.py` 只覆盖单轮调用，未覆盖"工具结果回填 →
再问一轮"这条路径。

**修法**（不动内核，通道内转换）：ollama 的 `_build_payload` 不再直接用 `to_chat_message`，
而是加一层 `_native_message(m)`：`role="tool"` 时把 `name` 改写成 `tool_name` 并丢弃
`tool_call_id`；assistant 的 `tool_calls` 照旧。

## 三、F2：非流式 `tool_calls` 未归一（🟡）

`openai_compat._oneshot` 直接 `yield {"tool_calls": msg.get("tool_calls")}` —— 原样透传。
实测（MockTransport）结果：

```
[2] 非流式 tool_calls 原样 = [{"id": "call_1", "type": "function",
                              "function": {"name": "f", "arguments": "{\"a\":1}"}}]
[2] 是否带 index = False
```

流式路径经 `_accumulate_tool_frag` 一定带 `index`。两条路径下游形状不一致：任何"按 index
聚合/排序"的消费方在非流式下会拿到 `None`。当前 Anthropic 线格式层不依赖 `index`，所以
没炸，但这是**隐患**而非无害差异。

**修法**：抽一个 `_normalize_tool_calls(raw)`（与 ollama 同名函数同语义），非流式也走一遍。

## 四、F3：Anthropic 强制工具选择 × 手工思考（🟡）

官方原文（扩展思考页）：

> Forced tool use (`tool_choice: {"type": "any"}` or `{"type": "tool", ...}`) is incompatible
> with manual extended thinking but works with adaptive thinking. The exceptions are
> Claude Fable 5.1 and Claude Mythos 5.1, which reject forced tool use on every request with a 400 error.

实机取证（`claude-sonnet-4-5` + `tool_choice="required"` + `thinking:True`）：

```
[1] anthropic thinking    = {"type": "enabled", "budget_tokens": 7168}
[1] anthropic tool_choice = {'type': 'any'}
```

两个字段同时出现 = 必然 400，而内核目前**不拦**。两条规则：

1. `thinking.type == "enabled"`（手工思考）与强制选择互斥 → 二者取一；
2. `claude-fable-5-1` / `claude-mythos-5-1` 上**任何情况**都拒强制选择 → 只能降级为 `auto`。

**修法**：`Profile` 增一个数据开关（如 `forbid_forced_tool: bool`），由 fable-5.1/mythos-5.1
规则置真；`_build_payload` 在"手工思考 + 强制选择"或"该模型禁用"时把 `tool_choice` 降级为
`{"type":"auto"}` 并在 `stats.extra` 里留一条 `tool_choice_downgraded` 说明做了什么
（静默改写会让调用方以为强制生效了）。取"降级"而非"抛错"的理由：与既有 GLM-5.3
"关不掉就降为最低档"的处理口径一致。

## 五、F4：ollama 下发 `tool_choice`（⚪）

实测：

```
[3] ollama payload 键 = ['messages', 'model', 'options', 'stream', 'tool_choice', 'tools']
[3] tool_choice = required
```

官方 api.md 的 `/api/chat` 字段全集是 `model / messages / tools / think / format / options /
stream / keep_alive`，**没有 `tool_choice`**；`/api/generate` 更是完全没有工具。

**修法**：ollama 的 `_build_payload` 不再透传 `tool_choice`（无据下发只会给"严格校验的
第三方 ollama 兼容服务"埋雷）。

## 六、F5：内核表达不了的能力（⚪）

| 能力 | 谁需要 | 缺什么 |
|---|---|---|
| `tool_result.is_error` | Anthropic 官方建议工具失败时置真 | `Message` 无错误位，`_blocks_for` 也无法产出 |
| `parallel_tool_calls` | OpenAI 系（是否允许并行调用） | `ModelParameters` 无此字段 |
| `disable_parallel_tool_use` | Anthropic | 同上 |
| `strict`（结构化函数调用） | OpenAI 系 | `Tool` 无此字段 |

这四项都是**增量**，不阻塞当前闭环；建议随"工具执行环"落地时一起定（内核现在只负责
下发 `tool_calls` 与接收回填，**谁执行、谁构造 `role="tool"` 消息在应用层**）。

## 七、验证情况

- 三条通道工具路径的现有用例：`test_anthropic_provider.py`（工具声明/选择/分片/非流式）、

- **F1 / F3 无对应用例** —— 前者是覆盖盲区，后者是新发现的契约冲突
