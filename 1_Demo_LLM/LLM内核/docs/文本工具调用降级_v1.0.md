# 正文文本工具调用降级 v1.0（No Native tool_calls → Parse from Text）

> 版本 v1.0 ｜ 2026-09-23 ｜ 来源：**厂商官方规格 + vLLM 解析器源码 + 40 项单元测试 + ollama 实机反例**
> 关联：`工具原生支持审计_v1.1.md`、`LLM内核架构_v1.4.md`

## 零、一句话

**不是所有端点都实现原生 function calling**。当模型把工具调用写进正文时，内核要能从正文里
把它抠出来，变成一个正常的 `tool_calls` 事件交给调用方 —— 且**不能把正常正文误吞成调用**。

新增文件：`palm_llm/providers/tooltext.py`（约 340 行），被三条通道共用。

---

## 一、为什么需要

| 场景 | 表现 |
|---|---|
| ollama + 自定义 GGUF（模板不含工具解析） | 调用被原样吐进 `message.content`，`tool_calls` 恒为空 |
| 第三方 OpenAI 兼容网关只做透明转发 | 同上 |
| 模型厂商自己的文本调用约定（Hermes / Llama3 / Mistral / Qwen2.5） | 调用是**正文里的固定标记**，需要按约定抠 |

用户侧的现象是"**明明声明了工具，模型也说要调用，可什么都没发生**"。
原生通道（`tool_calls` 字段）已经通了（见 v1.0 审计），这一层补的是**文本侧**。

---

## 二、各家族正文形态（官方依据）

| 家族 | 正文形态 | 依据 |
|---|---|---|
| Hermes / Qwen2 / Qwen3 | `<tool_call>{"name":…,"arguments":{…}}</tool_call>` | Qwen 官方 function_call 文档 |
| Llama 3.1+ | `<|python_tag|>{"name":…,"parameters":{…}}<|eom_id|>` | vLLM `llama3_json` 解析器 |
| Mistral | `[TOOL_CALLS][{"name":…,"arguments":{…}}]` | vLLM `mistral` 解析器源码 |
| Qwen2.5（旧模板） | `✿FUNCTION✿: name` + `✿ARGS✿: {…}` | Qwen v2.5 官方文档 |
| 社区 GGUF | ` ```json {"name":…,"parameters":{…}} ``` ` | 无官方文档，故校验最严 |

对应代码里的标记表：

```python
MARKERS = (
    ("<tool_call>", "</tool_call>"),
    ("<|python_tag|>", "<|eom_id|>"),
    ("[TOOL_CALLS]", None),          # None = 无结束标记，区域吃到流末
    ("✿FUNCTION✿", "✿RETURN✿"),
    ("```json", "```"),
)
```

参数键名三种都认：`arguments`（Hermes/Mistral）、`parameters`（Llama3/部分 GGUF）、
`tool_arguments`（个别实现）。外层包装也三种都认：裸对象、数组、
`{"tool_calls": [...]}`。

## 三、三条安全阀（**同时**满足才认，否则原文原样放行）

1. **本次请求声明了 tools** —— 没声明工具时模型不可能"在调用"；
2. **解析出的 `name` ∈ 已声明工具名**；
3. **区域内必须能解析成 JSON**。

```
没声明工具      → 过滤器整个关闭（连标记都不看）
name 不在声明里 → 判为普通正文
区域内不是 JSON → 连标记一起原样放行
```

第 2 条**不是形式主义**：本项目自己就会在文档、代码注释、聊天内容里输出讲解
`<tool_call>` 的示例。只看标签形态的实现会把示例吃成一次真实调用 —— 那是**静默地把用户
的文档变成一次工具执行**，比不解析危险得多。

安全阀 1 在三条通道上都有落地，且**降级通道自动继承**：`openai_compat` 的三级容错降级
会丢掉 `tools`（工具轮次整体不可用），此时 `declared_names(body.get("tools"))` 自然为空集，
过滤器自动关闭，无需额外判断。

## 四、流式安全设计

正文逐帧到来，不能等收完再判断（那等于放弃流式）。做法是把"标记可能还没收全"的那一小段
**扣住不发**：

```
标记之外：空留 (最长标记长度 - 1) 个字符，尾部留到下一帧补齐
标记之内：缓冲到结束标记出现
```

被扣住的内容只有两种归宿 —— 校验通过成为 `tool_calls`，否则**原样放行**。
因此正文流**不丢字、不重复、顺序不变**。

### 实现期踩到的四个坑（都已修，都有用例）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | 结束标记跨帧 | 逐字符喂时 `</tool_call>` 被拆到多帧，`buf.find(end)` 永远失败 → **区域永不合拢、内容丢失** | 区域内也只挪走"确定不含结束标记前缀"的部分，尾部留 `len(end)-1` 字符 |
| 2 | 未闭合区域凭空补字 | 到流末仍无结束标记时，放行内容被补上 `</tool_call>` —— 那些字符模型**从未输出** | `_close(out, closed=False)`：未闭合就不补结束标记 |
| 3 | Qwen 旧模板正则锚点错 | 扫描层已把 `✿FUNCTION✿` 剥掉，函数名正则却还在 body 里搜它 → **函数名永远解析不出** | 正则改为锚定 body 开头（`_FN_RE.match(body)`） |
| 4 | `[TOOL_CALLS]` 吞正文 | 无结束标记，区域吃到流末 → 调用 JSON 之后的正文被一并吃掉 | 区域右边界取"最后一个成功解析的 JSON 值"，其后作为**尾巴原样放行** |

坑 1 / 2 / 4 是同一个主题的三个面：**"流式 + 无常量边界"下的数据保真**。
判据统一为一条：**放行的正文 + 抽出的调用 == 模型的原始输出**。这条不变量有专门用例
（`test_no_call_text_is_lossless_at_any_frame_size` 用 5 种分帧尺寸逐字比对）。

## 五、事件路由：为什么是纯函数而不是生成器层

```python
text_tool_events(flt, ev) -> list[dict]     # 流式：一个事件就地过滤
filter_events(events, names) -> list[dict]  # 非流式：整段过一遍（复用同一份路由）
```

**刻意做成纯函数就地过滤，而不是再包一层异步生成器**。理由在 ollama 模块文档的
"单生成器约定"一节：三个 provider 的事件循环都承载着"调用方 `break` 早退时不重复 `aclose`"
的约束（实测会报 `RuntimeError: aclose(): asynchronous generator is already running`），
多嵌一层会让那个已修复的重入问题回来。

路由规则：

| 收到 | 动作 |
|---|---|
| `{"content": …}` | 喂给过滤器，返回可放行内容 |
| `{"tool_calls": …}` | **原生优先**：丢弃派生调用，把被扣的缓冲原样放行 |
| `{"done": …}` | `finish()` 结算；有派生调用则先追加 `tool_calls` 事件，再改 `finish_reason` |
| 其他（`reasoning` / `tool_call_delta`） | 原样透传 |

### 收尾帧的记账（不掩盖原值）

抽到的调用按 OpenAI 口径应表现为 `finish_reason == "tool_calls"`，否则**按 finish_reason
分支的调用方根本不会去执行工具**。但服务端原值不能丢：

```json
"stats": {
  "finish_reason": "tool_calls",
  "extra": {"finish_reason_vendor": "stop", "text_tool_calls": 1}
}
```

`text_tool_calls` 同时起到"这些调用是正文解析来的"的溯源作用 —— 与原生调用可区分。

## 六、刻意不支持的形态

### 6.1 GLM-4-0414 开源模板（裸名字 + 裸 JSON）

其调用是「函数名换行 + JSON 参数」，**没有稳定标签**，官方示例自带正则
`([^\n`]?)\n({.?})` 去抠。这类"裸名字 + 裸 JSON"规则会大面积误伤正常正文
（比如正文里出现一个 JSON 代码块），**故不纳入**。GLM 的 API 走原生 tools，不受影响。

### 6.2 实机反例：ollama 会剥掉标记只留裸 JSON

2026-09-23 实机取证（ollama 0.34.x + `qwen2.5:0.5b`，声明 tools 后要求模型复述标记）：

```
提示：请只输出这一行，不要解释、不要调用工具：
      <tool_call>{"name": "get_weather", "arguments": {"city": "北京"}}</tool_call>

返回 content： {"name": "get_weather", "arguments": {"city": "北京"}}   ← 标记没了，只剩裸 JSON
返回 tool_calls： []                                                   ← 原生也没给
```

说明两件事：

1. ollama 自带模型模板会**先剥掉 `<tool_call>` 标记**再交给内核 —— 所以对"模板已含工具
   解析的模型"，文本降级通常不会被触发；**它面向的是模板不含工具解析的自定义 GGUF**。
2. 这段裸 JSON 落在正文里，我们的过滤器**没有误吞它**（裸 JSON 本就不解析）。
   这是一次有价值的**负结果**：证明安全阀在真实输出上不放水。

## 七、与原生的优先级

```
原生 tool_calls 出现  →  派生调用作废（同一逻辑调用执行两份 = 副作用翻倍）
                         标记本身也属"已被消费的调用"，不写回正文（避免把标记泄漏给用户）
派生调用             →  在 done 帧一次性交出
```

两条都出现的场景是病态的；取"原生优先"因为原生是权威通道，且**派生那份作废比重复执行安全**。

**单元测试 40 例**（`tests/test_tool_text_fallback.py`）：

## 九、局限

- 标记表是**静态**的，厂商新增约定需要改 `MARKERS`（但这是有意的：自动"猜形状"会误吞正文）。
- `_REGION_CAP = 65536`：区域内一直不见结束标记就放弃解析、原文照发。防的是"模型跑飞时
  无上限缓冲"。
- 与 `reasoning` 通道无关：只扫 `content`，思考链里出现标记不会被视为调用（这是正确的，
  思考里的"我想调用 X"不是调用）。
