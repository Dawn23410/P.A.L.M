## 2. 三大协议阵营（官方确认）

| 阵营 | 端点 | 响应骨架 | 流式收尾 | 鉴权 |
|---|---|---|---|---|
| **A OpenAI Chat Completions** | `{base}/v1/chat/completions` | `choices[0].{message\|delta}` + `usage` + `finish_reason` | `data: [DONE]` | `Bearer` |
| **B Anthropic Messages** | `{base}/v1/messages` | `content[]` 类型块 + `stop_reason` | `message_stop`（**无 DONE**） | `x-api-key` |
| **C Gemini GenerateContent** | `/v1beta/models/{m}:generateContent`<br>流式 `:streamGenerateContent?alt=sse` | `candidates[].content.parts[]` + `finishReason` + `usageMetadata` | **无 DONE**，靠连接关闭 | **`x-goog-api-key` 头** |

**阵营 A 覆盖**：OpenAI / Azure、DeepSeek、智谱、通义千问(兼容模式)、Kimi、豆包(火山)、混元、MiniMax、零一、xAI Grok、Mistral、Groq、OpenRouter + 本地 vLLM/SGLang/LM Studio/llama.cpp/Ollama `/v1`。

🆕 **DeepSeek 同时提供两套格式**（官方）：`https://api.deepseek.com`（OpenAI）与 `https://api.deepseek.com/anthropic`（Anthropic）
→ 端点匹配**必须认 `/anthropic` 后缀**，否则会把 Anthropic 格式请求发给 OpenAI 通道。

## 3. 🆕 最硬的四条规则：多轮"必须回传"（不遵守直接 400）

这几条是**正确性红线**，不是兼容性微调：

| 厂商 | 规则（官方原文要点） | 违反后果 |
|---|---|---|
| **DeepSeek** | 带 `tools` 的请求，`reasoning_content` **必须在后续所有轮次回传**<br>（无 tool call 时中间轮可不传，传了会被忽略） | **400 错误** |
| **Kimi (K3)** | 多轮对话和工具调用时，将 API 返回的**完整 assistant message 原样**加入下一次请求，**不要只保留 content** | 上下文/推理断裂 |
| **Anthropic** | `thinking` 块带 `signature`，工具调用多轮**必须原样回传**；`redacted_thinking` 是**独立块类型**，也必须回传 | 改一字节即 400；只按 `type=="thinking"` 过滤会**静默丢块** |
| **腾讯云** | `reasoning_details[]`（含 `signature`）需**流结束后完整收集**并跨多轮回传 | 多轮推理断裂 |

→ **前置依赖**：这四条都要求内核 `Message` 能携带"不透明回传块"。
**现有 `Message.to_openai()` 是否带得动，尚未验证** —— 这是做 Anthropic / DeepSeek thinking 多轮的**前置门槛**。

## 4. 阵营 A 内部差异矩阵（官方口径）

| # | 差异点 | 官方事实 | 处理 | 级别 |
|---|---|---|---|---|
| 1 | **思考字段名** | `reasoning_content`：**DeepSeek / 智谱 / 火山豆包 / Kimi / 阿里云百炼** 官方均用此名；`reasoning`：OpenAI 官方、vLLM、ollama `/v1` | **双读**（本项目已修） | **A + B** |
| 2 | **SDK 不声明该字段** | Kimi 官方明确：`reasoning_content` **不在 SDK 类型定义中**，需 `hasattr/getattr` 读取 | 解析必须容忍未知字段 | **B** |
| 3 | **增量 vs 累积** | 见 §0：仅 **DashScope 原生协议**默认累积（`incremental_output` 默认 `false`）；QwQ / 思考模式 Qwen3 **只支持增量**；Qwen3 开源版不支持设 `false` | 兼容模式**无需处理**；接原生则请求显式加 `incremental_output:true` | **B** |
| 4 | **`finish_reason` 枚举** | 火山官方：`stop` / `length`（触发 max_token 或 max_completion_tokens 或 context_window）/ `content_filter` / `tool_calls`。豆包"**时机**"差异官方**未提及** | Profile 映射；时机差异待实机确认 | **B**（时机=C） |
| 5 | **usage 需显式开关** | OpenAI 官方：设 `stream_options.include_usage` 后会**多发一个 chunk，其 `choices` 永远是空数组**，其余 chunk 的 `usage` 为 `null`；流中断则收不到。Kimi 官方同建议 | 请求加 `stream_options`；解析容忍空 `choices` | **B** |
| 6 | **usage 明细** | `completion_tokens_details.reasoning_tokens`（OpenAI / DeepSeek / 百炼官方示例均有）；DeepSeek 另有 `prompt_tokens_details.cached_tokens` / `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | 可选读取 | **B** |
| 7 | **tool_calls 流式** | 官方一致：首个 chunk 带 `id/type/function.name`，后续只补 `arguments` 片段，**必须按 index 追加拼接、不能覆盖**；Kimi 明确"待流结束后再解析 JSON" | 已实现 | **B** |
| 8 | **思考开关（4 种写法）** | DeepSeek 官方：`extra_body={"thinking":{"type":"enabled/disabled"}}` + `reasoning_effort`(low/high/max)<br>智谱官方：GLM-4.7 用 `thinking:{type}`；**GLM-5.3 强制开启、关闭报错**，只能用 `reasoning_effort`(low/high/max，默认 max)<br>Kimi 官方：K3 始终开思考 + `reasoning_effort`(默认 max)；kimi-k2.7-code **temperature 不可改**<br>百炼官方：`enable_thinking`（Qwen/ERNIE） | **Profile 统一翻译**（ollama provider 已验证此思路有效） | **B** |
| 9 | **思考模式下禁用采样参数** | DeepSeek 官方：思考模式**不支持** `temperature` / `top_p` / `presence_penalty` / `frequency_penalty`，**设了不报错但无效** | 无需处理，但要知道设了没用 | **B** |
| 10 | 🔴 **`stop` 语义相反** | 腾讯混元官方："调用 OpenAI 接口时模型停止在匹配 stop 的内容**之前**；调用混元接口时停止在**之后**"，且"未来可能修改" | **Profile 标记**，需应用层知晓 | **B** |
| 11 | **厂商独有参数** | 智谱 **`tool_stream=True`**（GLM-5.1/5/4.7 支持工具调用流式输出）；智谱流式 `finish_reason` 与 `usage` **仅在最后一个 chunk** | Profile 声明 | **B** |
| 12 | **错误格式** | 腾讯云官方：流式出错时会在 SSE 中插入 `data: {"error":...}` 帧再 `[DONE]`；**`error.code` 可能是字符串也可能是数字** | 解析兼容 string/int；检查 delta 里的 error | **B** |

## 6. 架构方案（不变）

```
providers/
  base.py            # BaseProvider + get_client + 共享流式/超时（已有）
  openai_compat.py   # 通用通道（已有，加 profile 注入）
  ollama.py          # 特化：原生 /api/chat（已有）
  anthropic.py       # 特化：Messages（P1）
  gemini.py          # 特化：GenerateContent（P1）
  profiles.py        # ★ 方言数据 + resolve()
  registry.py        # ★ 端点 -> (provider_cls, profile)
```

**Profile 是数据不是类**（避免每加一家就加一个类的 O(N) 爆炸）：

```python
@dataclass(frozen=True)
class Profile:
    name: str
    reasoning_keys: tuple = ("reasoning_content", "reasoning")
    finish_reason_map: dict = field(default_factory=dict)
    thinking_style: str = "enable_thinking"
    needs_reasoning_echo: bool = False      # 🆕 多轮是否必须回传思考（DeepSeek/Anthropic/Kimi）
    stop_semantics: str = "before"          # 🆕 混元是 "after"
    require_usage_option: bool = False
    vendor_params: dict = field(default_factory=dict)   # 🆕 如智谱 tool_stream
```

匹配：`显式 type ＞ 端点/域名特征 ＞ 通用通道`。

## 8. 诚实边界

1. **除 ollama 外全部未实机验证**（无各家 API key）。官方文档 ≠ 线上实际行为。
2. 仅剩一条 C 级：**豆包 finish_reason 时机差异**，官方只给枚举未提时机。
3. **Profile 按域名给，覆盖不了模型级差异**：GLM-5.2 与 GLM-5.3 对 `clear_thinking` 语义相反（C 级二手）；GLM-5.3 强制开启思考、关不掉。
4. **§3 的四条回传规则是硬门槛** —— 在 `Message` 能携带不透明回传块之前，做 Anthropic / DeepSeek-thinking 多轮都是不完整的。
5. 本内核**已确认兼容** `stream_options.include_usage` 的空 `choices` 帧
   （`openai_compat.py:119-124`：`usage` 在 try 外提取，`choices[0]` 有 `except (KeyError, IndexError)` 兜底）。
