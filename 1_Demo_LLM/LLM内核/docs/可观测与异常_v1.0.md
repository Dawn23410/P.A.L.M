## 0. 一句话

把内核的"出错"从**一句裸 `RuntimeError`** 升级为**可分类、可决策、可追溯**的三件套：
**类型化异常**（据错决策能不能重试）、**有界重试策略**（企业稳 / 个人快同一个旋钮）、
**结构化异步日志 + `request_id`**（排障时能把一次请求的全链路串起来）。

---

## 1. 定位：为什么这三件事属于「最下层地基」

内核的定位是**最下层建筑**。省钱的策略（语义缓存 / 模型路由 / 预算）属于上层，
但**异常处理与日志属于地基的承重结构** —— 因为：

- 只有内核知道"这次失败到底发生在哪一层"（连接 / 鉴权 / 参数 / 流中断），上层拿到的
  如果只是字符串，就只能靠 `in` 匹配猜，必然腐烂；
- 只有内核握着流式生命周期，"已产出内容后中断**绝不能重试**"这条铁律只有它拦得住；
- 只有内核能看到全部往返，`request_id` 必须从这里种下才能贯穿。

**判据沿用**（见 `适配层决策说明_v1.0.md`）：能用数据表达的写进数据（策略 = `RetryPolicy`），
必须用代码表达的写成薄文件（`errors.py` / `obs.py`）。

## 2. 类型化异常（`palm_llm/errors.py`，144 行）

### 2.1 兼容契约（最重要）

`PalmLLMError` **继承 `RuntimeError`**。历史调用方与测试都用 `except RuntimeError` 兜底，
换层级**不能把兜底打穿** —— 所以这是"更细的分类"，不是"新的体系"。测试已就此设断言。

### 2.2 层级表

| 类型 | 触发 | 可重试 | 谁该处理 |
|---|---|---|---|
| `TransportError` | 连接重置 / 各类超时 / DNS / 首字节超时 | ✅ | **内核自动重试**（有界、按策略退避）；耗尽后交上层 |
| `UpstreamServerError` | 上游 5xx | ✅（标记） | **内核不重试**（避免故障期放大压力）；按 `retryable` 标记交上层决定 |
| `RateLimitError` | 429 | ✅（标记） | **内核不重试**；上层据标记自行退避重试/提示"稍后再试"（内核**不解析**上游 `Retry-After` 响应头） |
| `AuthError` | 401 / 403 | ❌ | **上层**：提示去补/换 Key，重试无意义 |
| `BadRequestError` | 其它 4xx | ❌ | **上层**：请求参数问题；降级通道另行处理字段超集 |
| `NotConfiguredError` | 本地未填 API Key 等 | ❌ | **上层**：UI 引导配置 |
| `StreamInterruptedError` | **已产出内容后**中断 | ❌ **绝不** | **上层**：把已产出部分交出去，问用户是否重发 |
| `CapabilityError` | 输入超出模型能力（发请求前拦） | ❌ | **上层**：照错误提示改输入 |

> **内核内重试只覆盖「传输层失败」**（连接重置 / 超时 / DNS / 首字节超时），且**必定有界**、
> **已产出内容后绝不重试**。**状态码错误（含 429 / 5xx）一律不在内核内重试** —— 内核只做
> **分类 + 打 `retryable` 标记**，重试与否交上层决策。该口径由
> `tests/test_retry_wiring.py::test_429_is_rate_limited_and_not_retried_by_transport`
> （断言请求只发 1 次）钉死，与 `base.py::_run_with_retry` docstring「协议错误 4xx/5xx 不可重试」一致。

> `CapabilityError` 原定义于 `providers/capability.py`，现统一到 `errors.py`，`_capability.py`
> 仅重导出以保持既有导入路径不变。

### 2.3 分类器

- `classify_error(message, *, status=…, retry_after=…)` —— 状态码 → 类型；
- `classify_error(message, *, exc=…, interrupted=False)` —— 传输异常 → 类型，
  `interrupted=True` 归 `StreamInterruptedError`（**防重复生成的关键分支**）。

**文案一律由调用方给定**（各家错误体形态不同，内核不做统一改写）；内核只负责选类型 +
挂上下文（`provider` / `model` / `status` / `retry_after` / `request_id`）。

## 3. 有界重试（`palm_llm/retry.py`，66 行）

### 3.1 三条铁律

1. **只重试"可重试"的**：`is_retryable` 只看 `PalmLLMError.retryable`，**默认 False**（安全侧）。
2. **已产出内容绝不重试**：流式下一旦 yield 过 chunk，失败一律归 `StreamInterruptedError`，
   宁可让上层决定，也不重新生成（重复输出 + 重复计费）。
3. **必须有界**：`max_attempts` 封顶，指数退避 + 上限，不无限重试。

### 3.2 策略数据（同一个旋钮的两端）

`ProviderConfig.retry`（缺省 `None` → `DEFAULT`）：

| 预设 | max_attempts | base_delay | jitter | 场景 |
|---|---|---|---|---|
| `LOW_LATENCY`（**默认**） | 2 | 0.0 s | 0 | 个人桌面：重试 1 次且不退避，不拖首字 |
| `STABLE` | 3 | 0.5 s | 0.3 | 企业部署：过故障期，抖动打散惊群 |

退避公式：`min(base_delay * 2^(attempt-1), max_delay)`，`jitter` 按比例浮动；
**若上游给了 `Retry-After`，优先照做**（既不打脸，也最快恢复）。

> 默认档与内核**既有行为完全一致**（原来就是"最多重试 1 次、不退避"），
> 所以本次落码对现有调用方是**零行为变更** —— 测试 180→214 全绿即证。

## 4. 结构化日志（`palm_llm/obs.py`，135 行）

### 4.1 低延迟铁律

- **热路径零阻塞**：`QueueHandler` 入队，真实 I/O 在后台线程（`QueueListener`）；
  `log_event` 只做一次入队。**绝不 per-token 打日志**。
- **默认安静**：级别由 `PALM_LLM_LOG` 控制（默认 `WARNING`：错误/重试可见；`INFO`/`DEBUG`
  需显式打开）。**未开启该级别时 `log_event` 只是一次整数比较 —— 无 I/O、无线程。**

### 4.2 `request_id` 贯通

- `contextvars` 承载，跨 `await` 自动传播，无需逐层传参；
- **服务层在回合边界种下**（`server/chat.py::run_chat` 首行 `set_request_id(None)`）；
- provider 被直接调用（无服务层）时，`_begin()` 里的 `request_id()` 自带兜底生成。

### 4.3 记录格式与纪律

```
2026-09-23 12:07:25.816 WARNING [a1b2c3d4e5f6] retry.scheduled  provider=t model=m attempt=1 delay=0.0 error=ConnectError
```

- 字段：`时间 级别 [request_id] 事件 key=value …`；
- 事件：`request.start`(debug) / `retry.scheduled`(warning) / `degrade.retry`(warning) /
  `chat.turn.done`(info) / `chat.turn.error`(error)；
- **绝不记录密钥与正文**：`log_event` 只落显式传入的结构化字段，不自动抓取 messages
  （prompt 正文含用户隐私与人设，不进日志是纪律不是偏好）。

### 4.4 服务层的错误事件（附加字段）

`run_chat` 的 error 事件新增 **附加**字段（后端兼容，前端可选用）：

```json
{"type": "error", "message": "...", "error_type": "RateLimitError",
 "retryable": true, "request_id": "a1b2c3d4e5f6"}
```

前端可据 `retryable` 决定要不要提示"重试"（限流/超时值得重试，参数错/鉴权错不该重试）。

## 5. 企业稳定 ↔ 个人低延迟：平衡点在哪

**代码同一份，策略可切** —— 这是本次设计的核心论点：

| 维度 | 个人低延迟（默认） | 企业高稳 |
|---|---|---|
| 重试次数 | 2（1 次） | 3 |
| 退避 | 0（不等） | 指数 + 抖动 |
| 日志级别 | WARNING | INFO/DEBUG + 全量 trace |
| 代价 | 故障期可能多失败一次 | 每次失败多等几秒 |

两者**不是两套代码，是同一个 `RetryPolicy` 的两端**。个人要的"快"和企业要的"稳"，
在这里是同一个旋钮 —— 该有的机制（分类、有界、不重复计费、可追溯）两边都有。

---

## 6. 与既有 telemetry 的分工

- **telemetry**（`providers/_telemetry.py`）管**成功路径的度量**：TTFT / TPOT / 缓存命中 / 输出速度；
- **obs**（本次）管**失败路径与生命周期**：错误分类 / 重试 / request_id 关联；
- 二者不重叠：telemetry 不关心成败之外的事，obs 不重复计算耗时。日志里的 `chat.turn.done`
  直接复用 telemetry 已算好的数字，不再算一遍。

## 8. 局限（诚实清单）

1. **重试只覆盖传输层与首字节超时**：`429`/`5xx` 目前**只分类不自动重试**（`is_retryable`
   标了 ✅，但 provider 的重试循环仍只捕获 `httpx.TransportError`/`FirstByteTimeout`）。
   要让 429/5xx 也自动退避重试，需在各 provider 循环里再接 `is_retryable` 分支 ——
   **本次未做**（避免改变既有行为；已验证不改也能跑通）。
2. **无熔断（circuit breaker）**：连续失败不会自动"跳闸"停发。企业级需要，个人桌面不需要。
3. **无 `Retry-After` 头解析**：`retry_after` 只能由调用方从错误体里取，内核未自动解析
   响应头（各家头名不统一）。
4. **`request_id` 未回写 `stats`**：目前只在日志与 error 事件里；未进 `stats.extra`。
5. **日志未落文件**：默认只输出到 stderr；落盘/轮转由调用方接 handler。
6. **`run_chat` / `ollama.complete` 等既有函数超 50 行**（历史遗留，非本次引入），
   未在本次重构 —— 遵守"最小修改"。
