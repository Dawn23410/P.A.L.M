# 适配翻译层决策说明 v1.0

> 决策问题：**是否需要做一层适配翻译层，以适应"同功能不同字段"的情况，目的是减少内核 API 数量？**
> 结论：**不需要做"一个大翻译层取代所有 provider"；需要做的是把两个方向分别归一 —— 而这件事
> 已经做了 2/3，本轮补上的是最后 1/3（响应方向）。**
> 日期：2026-09-23

## 一、先把目标拆开：要减少的到底是哪种"API 数量"

| 口径 | 现状 | 加一个原生通道后的变化 |
|---|---|---|
| **对外 API**（调用方看到的） | `provider.complete(messages, params, model, stream)` 一个 | **不变，仍是 1 个** |
| 内部协议实现类 | 3 个（openai_compat / ollama / anthropic） | +1 |
| 内部线格式转换文件 | 1 个（新拆的 `anthropic_wire.py`） | +1 |

**关键事实：加 Anthropic 原生通道不增加任何对外 API。** 调用方仍然只调 `complete()`，
拿到的仍然是同一种事件流。所以"为了减少内核 API 数量而做翻译层"这个动机本身不成立 ——
它要减少的东西（内部类个数）不是接口面积，而是实现个数。

而"内部实现个数"这个数字，**恰恰是应该随着协议数增长的那个数**。下面说明为什么。

## 二、差异分三层，能"翻译"的只有一层

### 第 1 层：字段级差异 —— 可翻译，已做

同一功能换个键名或换个枚举，例如：

| 功能 | 各家字段 |
|---|---|
| 思考开关 | `thinking:{type}` / `enable_thinking` / `reasoning_effort` / `think` |
| 最大输出 | `max_tokens` / `max_completion_tokens` / `num_predict` |
| 缓存命中 | `cached_tokens` / `prompt_cache_hit_tokens` / `cache_read_input_tokens` |

这一层**已经有翻译层**：`profiles.py`（引擎）+ `profiles_data.py`（数据）。
它是**数据驱动**的 —— 加一个模型是加一条 `ModelRule`，不是加一个类。
这正是"减少代码量"的正确做法，且已经落地（18 个用例）。

> 补充：`openai_compat.py` **本身就是一层翻译层** —— 它把 10 家供应商的方言
> 翻译成统一的 OpenAI 形状。所以"有没有翻译层"的答案是：有，而且在用。

### 第 2 层：响应形状差异 —— 可归一，本轮补上

同一件事算出来的数不同，或同一个字段的口径不同：

- OpenAI 的 `prompt_tokens` **含**缓存命中，Anthropic 的 `input_tokens` **不含**；
- Anthropic 不单列思考 token（另外两家单列）；
- 只有本地引擎给得出预填充/解码分段耗时。

这一层**不能只做键名映射**（会算出错的数），必须做**口径归一**。
本轮的 `telemetry.py`（回传拆分器）就是它：三家 usage 归一成一套字段 + 一套口径。

### 第 3 层：协议结构差异 —— **翻译层盖不住**

| 结构差异 | 为什么翻译表表达不了 |
|---|---|
| Anthropic 的 system **外提**为顶层参数 | 不是"改个键名"，是**换了个位置层级**；messages 里根本没有 system 角色 |
| `role="tool"` → **user + `tool_result` 块** | 一条消息**变成另一角色的消息**，且必须与前面的 `tool_use` **成对出现、顺序对应** |
| 流式是**块级生命周期** | OpenAI 是"每帧一个 delta"，Anthropic 是 `block_start → delta* → block_stop`；一个"心跳帧决定后续帧归属哪个块"的状态机，翻译表没有地方表达"状态" |
| `signature_delta` 思考签名 | 无对应物；且必须原样回传，**改一个字节即 400** |
| `max_tokens` 在 A 必填、B 可选 | 必填性是**约束**不是字段，翻译表只描述字段 |

把这一层硬塞进一个中心翻译器，会得到三个后果：

1. **漏**。结构性特性每上一个就漏一个（`signature_delta` 就是典型：字段映射清单里
   根本没有"签名"这个概念的位置）。
2. **中心文件成为所有厂商改动的汇聚点**。每家上新特性都要改同一个文件 → 违反单一职责，
   且改动风险面从"一家"扩大到"全部"。
3. **排障失真**。`400` 到底是"传输/鉴权问题"还是"翻译错了"，混在一个文件里看不出来。
   本轮把 `anthropic_wire.py` 拆出来的直接收益就是：传输（重试/超时/降级）与
   翻译（块映射/结构转换）是两件可分别测试的事。

## 三、三方案对比

| 方案 | 对外 API 数 | 内部复杂度 | 新增一家结构的成本 | 风险 |
|---|---|---|---|---|
| **A. 每协议一实现**（现状） | 1 | N 个薄适配器 + 1 个数据文件 | 新增 1 个 ≤300 行文件 | 各家实现可能漂移（靠共享件 `base.py` + 事件契约收敛） |
| **B. 一个大翻译层统吃** | 1 | 1 个中心文件持续膨胀 | **每次都要改中心文件**，改动面覆盖全部厂商 | 结构差异漏表达、上帝对象、排障困难 |
| **C. 混合**（A + 数据驱动字段层） | 1 | 同上 + `profiles` 数据 | 字段差异改**数据**；结构差异新增薄文件 | 需要判断"某差异属于哪层" |

**选 C，也就是现状。** 判据一句话：

> **能用数据表达的差异 → 写进数据；必须用代码表达的差异 → 新增一个薄文件。**
> 不要为了"看起来统一"把第二类硬塞进第一类。

## 四、什么情况下应该回头做中心翻译层（触发条件）

留着这几个信号，出现任意一条就该重新评估：

1. 出现**第 4 个、第 5 个**协议，且它们与 openai_compat 的字段差异仍在增长
   （说明字段层数据已经不够用，需要更强的表达力）。
2. 某个结构差异在**三个以上协议里重复出现**（例如三家都用块级流式），
   此时应把它提成**共享基类或共享解析器**，而不是继续各家复制 ——
   但那是"抽共享件"，仍然不是"中心翻译层"。
3. `anthropic_wire.py` 这类文件开始出现**跨协议 copy-paste**，说明抽象点找错了。

## 五、本轮实际做了什么（对应决策）

| 层 | 做的事 | 文件 |
|---|---|---|
| 字段层（出参） | 沿用数据驱动，不新增翻译层 | `profiles.py` / `profiles_data.py` |
| 响应层（入参） | **新建口径归一器** | `telemetry.py`（回传拆分器） |
| 结构层 | **新增薄适配器，并显式与传输分离** | `anthropic.py` + `anthropic_wire.py` |
| 共享件 | 三处重复的 `_feed` 合并为 `telemetry.feed` 一份 | — |

其中"响应层归一"是本轮补上的最后一块：之前只有出参方向有翻译层，入参方向各家
usage 字段是**原样透传**的，调用方要自己认 `cached_tokens` / `prompt_cache_hit_tokens` /
`cache_read_input_tokens` 三种写法 —— 那才是真正的"该有翻译层而没做"的地方。

## 六、一句话结论

> **不要为"减少 API 数量"做翻译层 —— 对外 API 本来就只有 1 个。**
> **要为"减少调用方的字段心智负担"做翻译层 —— 而那是数据（出参）与归一器（入参）的活，
> 不是中心翻译器的活。结构差异继续由每协议一个薄适配器承担，这是有意的成本，不是债。**
