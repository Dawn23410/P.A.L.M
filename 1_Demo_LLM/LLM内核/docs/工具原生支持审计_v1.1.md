## 二、F1：ollama 工具结果回填字段名（🔴 → 已修）

原来直接把 `Message.to_openai()` 的结果发出去，而 ollama 原生消息对象**只认 `tool_name`，
没有 `tool_call_id`，也没有 `name`**（官方 api.md 的消息字段表）。修法是通道内加一层转换：

```python
def _native_message(m: Message) -> dict:
    out = to_chat_message(m)
    if out.get("role") == "tool":
        out.pop("tool_call_id", None)
        name = out.pop("name", None)
        if name:
            out["tool_name"] = name
    elif out.get("tool_calls"):
        out["tool_calls"] = [_native_call(tc) for tc in out["tool_calls"]]
    return out
```

同时修掉同一处的第二个硬差异：assistant 的 `tool_calls[].function.arguments`
在原生协议里必须是**对象**，而内核口径是 JSON **字符串**（`_native_call` 负责还原）。

> 为什么 1.0 版没被测出来：原有用例只覆盖单轮调用，没覆盖"工具结果回填 → 再问一轮"。
> 单轮跑得通、多轮闭环断掉，是典型的**字段名静默失效**。

## 三、F2：非流式 `tool_calls` 未归一（🟡 → 已修）

`openai_compat._oneshot` 原先原样 `yield {"tool_calls": msg.get("tool_calls")}`，
而流式路径经分片累加**一定带 `index`**。两条路径下游形状不一致，任何"按 index 聚合/排序"
的消费方在非流式下会拿到 `None`。

归一函数**上提到 `base.py`**（而不是在 ollama 里再写一份）：

```python
normalize_tool_calls(raw)   # 补 index（缺了按位置补）/ 补 id / type 兜底 / arguments 对象→字符串
```

三条通道共用同一份 —— 两份实现必然漂移。ollama 侧保留 `_normalize_tool_calls` 作为薄别名，
不打断既有引用。

## 四、F3：Anthropic 强制工具选择 × 手工思考（🟡 → 已修）

官方原文（扩展思考页）：

> Forced tool use (`tool_choice: {"type": "any"}` or `{"type": "tool", ...}`) is incompatible
> with manual extended thinking but works with adaptive thinking. The exceptions are
> Claude Fable 5.1 and Claude Mythos 5.1, which reject forced tool use on every request with a 400 error.

两条规则分别落在**数据**与**代码**上：

| 规则 | 承载 | 值 |
|---|---|---|
| 强制选择 × 手工思考（`type:"enabled"`）互斥 | `anthropic._tool_choice_setup()` | 降级 `{"type":"auto"}` |
| Fable5.1 / Mythos5.1 任何情况拒强制选择 | `ModelRule.reject_forced_tool=True` | `profiles_data.ANTHROPIC` 新增一条 priority=110 规则 |

**取"降级"而非"抛错"**：与既有"GLM-5.3 关不掉思考就降为最低档"的处理口径一致（厂商硬契约
优先于调用方偏好，但不把整轮请求打死）。

**但不静默**——降级原因写进 `stats.extra.tool_choice_downgraded`：

```
notes["tool_choice_downgraded"] = "手工思考与强制工具选择互斥，已降级为 auto"
```

否则调用方会以为"必须调用"已经生效。这是本条的**关键点**：静默改写等于把 400 换成
"看起来成功但行为不同"，比报错更难查。

## 五、F4：ollama 下发 `tool_choice`（⚪ → 已删）

原生 `/api/chat` 的字段全集是 `model / messages / tools / think / format / options /
stream / keep_alive` —— **没有 `tool_choice`，也没有 `parallel_tool_calls`**；官方博客把
"Tool choice: force a model to use a tool" 列在 *Future improvements*，即尚未支持。
无据下发只会给"严格校验的第三方 ollama 兼容服务"埋雷，故直接不下发。

## 六、F5：表达不了的能力（⚪ → 已补 3 项）

| 能力 | 谁需要 | 落点 |
|---|---|---|
| `tool_result.is_error` | Anthropic 官方建议工具失败时置真 | `Message.tool_error` → `_blocks_for` 产出 `is_error` |
| `strict` | OpenAI 结构化函数调用 | `Tool.strict` → `function.strict`（默认 `None` = 不下发） |
| `parallel_tool_calls` | OpenAI 系 | `ModelParameters.parallel_tool_calls` → payload 顶层 |
| `disable_parallel_tool_use` | Anthropic | 由 `parallel=False` 并进 `tool_choice`（原生无独立字段） |

三条默认值都取"不表达"，理由一致：**不支持的端点收到未知字段可能直接 400，
而我们无法从模型名可靠推断支持性**，所以让调用方显式表达。

`tool_error` 只对 Anthropic 生效（OpenAI 系无对应字段，约定把错误文本写进 `content`），
`server/models.py` 的 `to_kernel()` 已同步带上这两个新字段。

## 七、F6：ollama 流式收尾帧绕过了工具过滤器（🔴，本轮新发现）

接入正文文本降级时暴露：ollama 流式路径在 `obj["done"]` 分支**直接 `yield` 收尾帧**，
没经过 `text_tool_events()`。后果是过滤器积累的调用与被扣住的尾巴**永远不会结算** ——
表现为"正文解析出的调用凭空消失"。

```
修改前：                       修改后：
yield {"done": True, ...}      tail = {"done": True, ...}
return                         for ev in text_tool_events(flt, tail):
                                   yield ev
                               return
```

两处（正常 `done` 帧、断流补帧）都已改为过过滤器。openai_compat 与 anthropic 的收尾帧
本来就走在过滤器内，无此问题。

   故该场景下调用仍走原生通道；文本降级面向的是"模板不含工具解析"的自定义 GGUF。详见
   `文本工具调用降级_v1.0.md` §六。

## 九、遗留

- **工具执行环仍不在内核**：内核只负责下发 `tool_calls` 与接收回填，谁执行、谁构造
  `role="tool"` 消息在应用层。F5 补齐的字段已为执行环留好位置。
- **`strict` 未在 Anthropic 通道表达**：原生无对应能力（`input_schema` 即强约束），
  故只对 OpenAI 系下发，这是有意的非对称。
