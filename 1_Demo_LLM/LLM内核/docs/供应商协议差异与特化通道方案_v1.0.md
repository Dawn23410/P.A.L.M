## 0. 一句话结论

**回传格式不通用，但分层后只有 3 个协议阵营 + 1 层"方言"需要适配：**

- **通用通道**（OpenAI Chat Completions）能吃下 **90%+** 供应商 —— 国内主流厂商几乎全部兼容；
- **必须特化的只有 3 个**：Anthropic Messages、Google Gemini、Ollama 原生（已做）；
- 阵营 A 内部剩下的一堆"小差异"（思考字段名、finish_reason 枚举、增量/累积）**不需要新 Provider 类**，
  用一层**方言 Profile（纯数据）**吸收即可，避免每加一家就加一个类的 O(N) 爆炸。

## 2. 三大协议阵营

### 阵营 A：OpenAI Chat Completions（事实标准）

**端点**：`POST {base}/v1/chat/completions`
**响应骨架**：`choices[0].{message|delta}` + `usage.{prompt_tokens,completion_tokens,total_tokens}` + `finish_reason`
**流式**：SSE，`data: {...}` + `data: [DONE]`

覆盖：OpenAI / Azure、DeepSeek、智谱 GLM、通义千问（兼容模式）、Kimi(Moonshot)、豆包(火山)、
腾讯混元、MiniMax、零一万物、xAI Grok、Mistral、Groq、Together、Fireworks、OpenRouter，
以及本地 vLLM / SGLang / LM Studio / llama.cpp server / Ollama `/v1`。

### 阵营 B：Anthropic Messages（**结构完全不同**）

- 端点 `POST /v1/messages`；请求 `system` 是**顶层字段**，不在 messages 数组里
- 工具定义 `{name, description, input_schema}`（不是 `function.parameters`）；**`max_tokens` 必填**
- 响应是 **`content[]` 类型块**：`text` / `thinking` / `redacted_thinking` / `tool_use`
- 结束原因是 `stop_reason`（`end_turn` / `max_tokens` / `tool_use`），不是 `finish_reason`
- usage 是 `input_tokens` / `output_tokens`；`output_tokens_details.thinking_tokens` 单独计思考
- 流式是**具名事件**：`message_start → content_block_start → content_block_delta → content_block_stop → message_delta → message_stop`，**无 `[DONE]`**

🔴 **两个必须特化的坑（会让"通用解析"静默出错）**：
1. **thinking 块带 `signature`，工具调用多轮必须原样回传**；改过一个字节就 400。
2. **`redacted_thinking` 是独立块类型** —— 若按 `block.type == "thinking"` 过滤再回传，会**静默丢掉** redacted 块并破坏多轮协议。

### 阵营 C：Google Gemini GenerateContent（又一套）

- 端点 `POST /v1beta/models/{model}:generateContent`，流式 `:streamGenerateContent?alt=sse`
- 请求 `contents[].parts[]` + 顶层 `systemInstruction`；工具进 `tools[].functionDeclarations[]`（JSON Schema → OpenAPI 3.0）
- 响应 `candidates[].content.parts[]`、`finishReason`(`STOP`/`MAX_TOKENS`/`SAFETY`)、
  `usageMetadata.{promptTokenCount,candidatesTokenCount,totalTokenCount}`
- 流式 SSE **没有 `[DONE]`**，靠 HTTP 连接关闭结束
- 鉴权是 **`x-goog-api-key` 头，不是 Bearer**

### 阵营 D（暂不处理）：OpenAI Responses API

`POST /responses`，具名生命周期事件（`response.output_text.delta` …），服务端状态。
**与 Chat Completions 不互通，如需支持是独立通道。**

## 3. 阵营 A 内部差异矩阵（这些**不需要**独立 Provider 类）

| # | 差异点 | 具体分裂 | 处理 | 可信度 |
|---|---|---|---|---|
| 1 | **思考字段名** | `reasoning_content`（DeepSeek/腾讯/多数国产）vs `reasoning`（OpenAI 官方、vLLM、ollama `/v1`、部分网关） | **双读**（本项目已修，已实机验证） | **A** |
| 2 | **思考字段结构** | 有的是字符串，有的是 `reasoning_details[]`（含 `signature`，**多轮需回传**） | Profile 声明是否需回传 | B |
| 3 | **增量 vs 累积** | 🔴 **已按官方文档更正**：累积是 **DashScope 原生协议**的默认行为（`incremental_output` 默认 `false`，每片为全文 `I`→`I like`→`I like apple.`）；**OpenAI 兼容模式官方示例是增量**。QwQ / 思考模式下的 Qwen3 **只支持增量**，Qwen3 开源版不支持设 `false`，Qwen3 商业版思考模式下需手动设 `true` | **兼容模式无需差分**；若接 DashScope 原生协议 → 请求里显式加 `incremental_output: true`（**事前防，而非事后差分**） | **B（官方文档）** |
| 4 | **finish_reason 枚举** | `stop` / `end` / 厂商自定义；豆包**返回时机**不同 | Profile 映射表 | C |
| 5 | **usage 细节** | `completion_tokens_details.reasoning_tokens`（百炼官方示例=153）；**需 `stream_options.include_usage` 才给**，且**最后一帧 `choices` 可能为空**、usage 单独成一帧 | 请求自动加 `stream_options`；解析需容忍空 `choices` | **B（官方）**；**本内核已兼容**（见 §8.6） |
| 6 | **流式收尾** | 有厂商在 `[DONE]` 前多发一个空 `data: {}`；Gemini 无 `[DONE]` | 通用容错 + 阵营 C 自管 | C |
| 7 | **tool_calls 增量** | 首片带 `id/type/name`、后续只补 `arguments` 片段（通用）；智谱 `index` 处理有微差 | 已实现 + Profile 微调 | C |
| 8 | **思考开关写法（4 种）** | `enable_thinking`(GLM/Qwen/ERNIE) ｜ `thinking:{type:"enabled"/"disabled"}`(DeepSeek/豆包/GLM-4.6+) ｜ `reasoning_effort`(OpenAI/GLM-5.3) ｜ `chat_template_kwargs.enable_thinking`(vLLM+Qwen3) | **Profile 统一翻译**（ollama provider 已用此思路做了 4→1） | B/C |
| 9 | **错误格式** | OpenAI 式 `error:{message,type,code}`；有的给扁平 JSON 甚至 HTML；**`error.code` 可能是字符串也可能是数字** | 解析时兼容 string/int | B |
| 10 | **鉴权** | Bearer 为主；Gemini `x-goog-api-key`；百度千帆 `bce-v3` 签名；智谱历史 JWT | 阵营级 + Profile | B |

> 第 8 项有个**实战教训**（二手）：部分思考模型默认开 thinking，而开思考时 `tool_choice` 等结构化输出能力受限，
> 表现为"绑了工具就调不动"，且报错完全不指向根因 → **必须显式传 enabled/disabled，绝不依赖服务端默认值**。

## 4. 特化判定

### 4.1 必须独立 Provider 类（协议级差异）

| 通道 | 理由 |
|---|---|
| `OllamaProvider` | **已完成**。原生 `/api/chat`，`think` 一等参数、`message.thinking`、纳秒分段耗时 |
| `AnthropicProvider` | content blocks + 具名事件 + 必填 max_tokens + thinking signature 回传 |
| `GeminiProvider` | contents/parts + usageMetadata + 无 DONE + x-goog-api-key |

### 4.2 只需方言 Profile（协议同 OpenAI）

DeepSeek / 智谱 / 千问 / Kimi / 豆包 / 混元 / MiniMax / Grok / 零一 / vLLM / SGLang / LM Studio / llama.cpp
→ **共用一个 `OpenAICompatProvider` + 各自 Profile 数据**。

匹配优先级：**① 显式 `cfg.type` ＞ ② 端点/域名特征 ＞ ③ 通用通道**

| 命中规则 | 走向 | Profile |
|---|---|---|
| `type: "anthropic"` / 路径含 `/v1/messages` / 域名 `api.anthropic.com` | `AnthropicProvider` | — |
| `type: "gemini"` / 域名 `generativelanguage.googleapis.com` / 路径含 `:generateContent` | `GeminiProvider` | — |
| `type: "ollama"`/`"ollama_native"` / 端口 `11434` 且非 `/v1` | `OllamaProvider` | — |
| 域名 `api.deepseek.com` | 通用 | deepseek |
| 域名 `open.bigmodel.cn` | 通用 | glm |
| 域名 `dashscope.aliyuncs.com` **或 `*.maas.aliyuncs.com`**（路径含 `/compatible-mode/`） | 通用 | qwen（**请求自动加 `stream_options.include_usage`**）<br>⚠️ 百炼是多地域端点（`{WorkspaceId}.{region}.maas.aliyuncs.com`），**只匹配 `dashscope.aliyuncs.com` 会漏** |
| 域名 `api.moonshot.cn` | 通用 | kimi |
| 域名 `ark.cn-beijing.volces.com` | 通用 | doubao |
| 域名 `api.hunyuan.cloud.tencent.com` | 通用 | hunyuan |
| 域名含 `minimax` / `lingyiwanwu` / `x.ai` / `api.mistral.ai` / `api.groq.com` | 通用 | 对应（先给最小 profile） |

> **设计原则：未命中一律走通用，不改变现状**（现在所有未知供应商本来就是走通用）。
> 匹配只做"加分"，不做"拦截"。

## 6. 架构方案：协议层 / 方言层分离

```
providers/
  base.py              # BaseProvider + get_client + 共享流式/超时（已有）
  openai_compat.py     # 通用通道：阵营 A 全吃（已有，加 profile 注入）
  ollama.py            # 特化：原生 /api/chat（已有）
  anthropic.py         # 特化：Messages（P1）
  gemini.py            # 特化：GenerateContent（P1）
  profiles.py          # ★ 新增：方言数据 + resolve()
  registry.py          # ★ 新增：端点 -> (provider_cls, profile)
```

### 6.1 Profile 是**数据**不是类

```python
@dataclass(frozen=True)
class Profile:
    name: str
    reasoning_keys: tuple = ("reasoning_content", "reasoning")  # 思考字段别名
    reasoning_needs_echo: bool = False      # 是否需多轮回传（signature）
    cumulative_delta: bool = False          # 🔴 千问：累积返回需做差分
    finish_reason_map: dict = field(default_factory=dict)   # {"end": "stop"}
    thinking_style: str = "enable_thinking" # 开关写法
    usage_details: bool = False             # 是否有 *_details
    require_usage_option: bool = False      # 是否需 stream_options.include_usage
```

### 6.2 匹配入口

```python
def resolve(base_url: str, type_: str | None = None) -> tuple[type, Profile]:
    if type_ and type_ in PROVIDERS:            # ① 显式优先
        return PROVIDERS[type_], profile_for(type_)
    for pattern, (cls, prof) in ENDPOINT_RULES: # ② 端点特征
        if pattern in base_url:
            return cls, prof
    return OpenAICompatProvider, GENERIC        # ③ 未命中走通用
```

### 6.3 与 ollama 既有做法保持一致

`OllamaProvider` 里已验证有效的 **`_resolve_think()`（4 种写法 → 原生 `think`）**
就是这个 Profile 思路的雏形 —— 本方案把它**提升为通用机制**，而不是每家重写一遍。

## 8. 诚实边界与风险

1. **本文件除标注 A 的条目外，均未实机验证**；C 级条目（千问 cumulative、豆包 finish_reason 时机、智谱 index）**落码前必须先验**。
2. **自动匹配只能匹配"已知规则"**。同域名下不同模型行为仍可能不同 —— 例：GLM-5.2 与 GLM-5.3 对
   `clear_thinking` 的**语义完全相反**（二手，C 级）。Profile 按域名给，无法覆盖模型级差异。
3. ~~cumulative 用运行时探测~~ → **已作废**。官方证实累积只发生在 DashScope **原生协议**
   （`incremental_output` 默认 `false`），OpenAI 兼容模式是增量
   → **应在请求侧显式传参防，不需要运行时差分**。将来若真接 DashScope 原生，
   做法是"请求加 `incremental_output:true`"，而不是"收到后做差分"。
   （教训：二手对比文章把两套协议混为一谈，差点据此做出一个错误设计。）
4. **thinking signature 回传**要求 `Message` 结构能携带"不透明回传块"。
   现有 `Message.to_openai()` **是否带得动**，需先确认 —— 这是 Anthropic 通道的前置依赖。
5. **未命中一律通用通道** = 现状，不会让任何现有供应商变差。
