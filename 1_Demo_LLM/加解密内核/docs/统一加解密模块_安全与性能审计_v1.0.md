## 1. 速度基准（真实实测，1KB 负载除注明外）

> ℹ️ 本表为 **2026-09-09（纯 Python 后端）** 那次运行的口径，**不可与当前 json 直接对比**：
> `bench_crypto_audit.json` 已于 2026-09-23 在 **C 后端（tongsuo / tongsuopy 1.0.1）**
> 下重跑，整体快 2 个数量级（json 的 `env.backend` 自述口径）。同后端同口径复跑
> 另有 ±10% 级抖动，属正常运行方差。原始数据以 json 为准。

| 项目 | p50 | p95 | 吞吐 |
|---|---|---|---|
| SM3 哈希 (1KB) | 3.570ms | 3.937ms | 0.29 MB/s |
| SM4 encrypt_text（MemoryCipher 底层，base64 落库） | 3.658ms | 3.978ms | 0.28 MB/s |
| SM4 decrypt_text | 3.578ms | 3.928ms | 0.29 MB/s |
| SM4 纯吞吐 (64KB) | 349.97ms | — | **0.19 MB/s** |
| **MemoryCipher 典型记忆条目（~200字/600B）** | **2.594ms** | 2.908ms | — |
| vault encrypt_data（含 HMAC-SM3） | 7.844ms | 8.606ms | 0.13 MB/s |
| vault decrypt_data（含 HMAC-SM3） | 7.454ms | 8.169ms | 0.14 MB/s |
| PBKDF2-HMAC-SHA256 derive_key（200k 轮） | 49.19ms | 50.96ms | 一次性 |
| vault.boot() 装配（指纹+密钥库落盘） | 66.26ms | 67.98ms | 一次性 |
| SM2 信封加密 / 解密 (1KB) | 24.69 / 21.33ms | — | 0.04–0.05 MB/s |
| ~~SM2 签名 / 验签 (1KB)~~ | 8.19 / 11.52ms | — | **已作废：签名族于 v0.5.0 移除** |
| **file_ops encrypt_file (1MB, 含 IO)** | **7265.9ms** | 7413.6ms | **0.14 MB/s** |
| **file_ops decrypt_file (1MB, 含 IO)** | **6941.5ms** | 7065.7ms | **0.15 MB/s** |

**读法**：
- 记忆层主路径（MemoryCipher 单条）p50 2.6ms——对比同批实测的 VectorMemory add 总耗时
  p50 49.6ms，加密占比 ~5%，**对交互延迟无感**。
- PBKDF2/boot/SM2 都是一次性或低频操作，不在热路径。
- vault 路径比裸 SM4 慢一倍（7.8 vs 3.7ms），是 HMAC-SM3 认证标签的代价——
  换来"篡改必被拒"，属于用得起的安全开销。

## 2. 安全验证（10/10 PASS）

| # | 验证项 | 结果 | 说明 |
|---|---|---|---|
| S1 | 篡改密文拒绝 | ✅ | HMAC-SM3 拦截，抛 ValueError |
| S2 | 篡改 MAC 拒绝 | ✅ | 尾部 32B 校验码翻转即拒 |
| S3 | 错误密钥拒绝 | ✅ | 换密钥解密必失败 |
| S4 | 换机指纹解封拒绝 | ✅ | 密钥库以 PBKDF2(指纹) 密封，跨机必拒 |
| S5 | IV 唯一性 | ✅ | 同明文加密 1000 次，IV 1000/1000 唯一（2^128 随机空间） |
| S6 | 明文不泄露 | ✅ | 密文中不含明文字节序列 |
| S7 | MemoryCipher 篡改返回空串 | ✅ | SM3 完整性标签拦截，不返回错误内容 |
| S8 | 边界输入 | ✅ | 空串 / 16B 对齐 / 1MB 全部正确 round-trip |
| S9 | 常量时间 MAC 比较 | ✅ | `hmac.compare_digest`（本次加固项） |
| S10 | 恢复密钥导入路径 | ✅ | 32 位 hex 主密钥明文导入后可解密（换机恢复闭环） |

**构造正确性**：Encrypt-then-MAC（先 SM4-CBC 后 HMAC-SM3）· 随机 IV 前置 · PKCS7 ·
PBKDF2(200k 轮) 密封密钥库 · 密钥与硬件指纹解耦（恢复密钥可换机解密）。
密码强度：SM4-128 / SM3-256 / SM2-256，均为国标商用密码算法。

## 3. 本次审计加固项（已落地）

1. **MAC 比较改常量时间**：`decrypt_data` / `unseal_keystore` 原用 `==` 逐字节比较，
   存在 MAC 定时侧信道；改为 `hmac.compare_digest`（2 处）。
2. **boot() 补捕 OSError**：原只捕 `RuntimeError`——磁盘满 / 权限不足 / 路径不可写时
   `FileNotFoundError` 会**炸穿**"失败仅降级禁用"的设计承诺。补 `(RuntimeError, OSError)`，
   已实测不可写路径下 boot 优雅降级（`bound=False`，不抛异常）。

## 4. 局限与诚实披露

1. **吞吐硬瓶颈：gmssl 为纯 Python 实现**，实测 0.13–0.29 MB/s。大文件场景
   1MB≈7.3s、100MB≈12min——这不是调参能解决的，是解释器级瓶颈。
2. **HMAC-SM3 也是纯 Python**（逐字节循环），vault 每次加解密比裸 SM4 多 ~4ms；
   高频小对象场景可接受，批量场景雪上加霜。
3. **密钥派生用 PBKDF2-HMAC-SHA256**（非国密组件）。若要求"全栈国密合规"
   （如等保/密评），需换 PBKDF2-HMAC-SM3 或 SM3-KDF；仅自用加密则无碍。
4. **密钥驻留内存不可零化**：Python 字节串无法保证擦除，内存取证可提取主密钥
   ——单机桌面场景的通用限制，非本实现特有。
5. **单进程全局主密钥**：`set_master_key` 为模块级状态；多进程需各自 boot（密钥库
   文件原子写 `tmp+replace` 保证不损坏，但主密钥各自独立注入）。
6. **macOS 无主板指纹源**：`boot()` 会采集失败 → 自动降级禁用（不报错但加密不可用）。
   支持 Windows（BIOS 注册表）/ Linux（dmidecode/sysfs）。
7. **CBC 无并行加密**：对比 CTR/GCM 模式在多核上无加速空间（纯 Python 下无实际差异）。

## 5. 生产就绪判定与建议

**判定：分场景可用。**

- ✅ **P.A.L.M 记忆层落盘加密（设计目标场景）：批准上生产**。前提仅
  `pip install gmssl`；单条 2.6ms 延迟无感，安全机制完整，失败路径全部降级不炸主流程。
- ✅ 密钥库 / 配置文件 / KB 级敏感小文件：可生产。
- ❌ **MB 级以上批量文件加解密：不要用本模块**。若确有需求，三条路：
  1. 接 GmSSL C 命令行 / Rust binding（吞吐可提 2~3 个数量级）；
  2. 大文件用分块 + 仅对索引/头部加密的混合方案；
  3. 明确放弃国密约束时用 `cryptography`（AES-NI），但那是另一个模块的职责。

**换机/灾难恢复预案（必须写入运维手册）**：密钥库文件（`.keys/.crypto_keystore`）
+ 32 位 hex 恢复密钥两者都要离线备份——只有恢复密钥即可在新机 `set_master_key`
解密历史数据；两者皆失 = 数据不可恢复（无后门，这是特性不是缺陷）。

## 7. v0.5.0 范围收缩与泄露点加固（2026-09-22）

### 7.1 范围收缩（有意为之，非缺依赖）

算法矩阵由「能力铺开」收敛为「够用集」：**6 族 / 16 条**，缺口报告 0 条
（`palm_cryptokernel.capabilities.report()` 可复现）。移除的三族与理由见 README 的范围边界。

| 族 | 处置 | 说明 |
|---|---|---|
| sign（签名） | **整体移除** | 单机单用户无不可否认需求；完整性由 HMAC 承担。SM2 签名接口（`sign_with_sm3` / `verify_with_sm3`）一并移除 |
| kem（后量子封装） | **整体移除** | 常规公钥加密（SM2 / RSA）已够用，且少一片攻击面 |
| kex（密钥协商） | **整体移除** | 单机无对端可协商 |
| hash 的 md5 / sha1 槽位 | **移除**（v0.5.2） | 原按"读旧数据"假设留的兼容档，复核后该假设**不成立**（存量指纹全部由 sm3/sha256/sha512 产生）、且内核**零消费者**。`legacy` 只是标记、**不阻止调用**，弱算法留在安全面里迟早会被用上 ⇒ 清掉比留着标记更安全 |

`envelope` 由「KEM + AEAD」改为「**公钥信封**」：数据密钥改由 SM2 / RSA 封装，
报文版本号由 1 升到 2（v1 的 KEM 报文格式不同，明确不支持、不兼容）。

保留矩阵（16 条）：hash 3（sm3 / sha256 / sha512）· mac 3（hmac-sm3 / sha256 / sha512）·
kdf 3（argon2id / pbkdf2 / hkdf）· cipher 2（sm4-cbc / aes-256-cbc）·
aead 2（aes-256-gcm / chacha20-poly1305）· pubkey 3（sm2 / rsa-oaep / rsa-pkcs1v15）。
`rsa-pkcs1v15` 仍带 `legacy=True`（旧填充，仅供兼容）。

> **诚实披露**：`absent()` 为空**不代表「能力全齐」**，而代表「申报清单已被满足」。
> 被移除的算法属**范围决策**，已在 `abcs.py` 的「范围边界」段落与 README 中显式列明，
> 不塞进缺口清单冒充「缺依赖」。

### 7.2 泄露点加固（8 项，均已实测验证）

| # | 问题 | 修法 | 验证 |
|---|---|---|---|
| L1 | 密钥文件、密钥库、解出的明文**以默认权限落盘**（POSIX 上可被同机其它用户读） | 新增 `_private_fs.py` 统一收敛：POSIX 用 0600 / 0700，Windows 用 `icacls /inheritance:r /grant:r`；自管目录带 `(OI)(CI)` 继承位、文件按**身份**（`st_dev,st_ino`）缓存，**同一对象只收紧一次**（v0.5.1） | 实测返回 True（本机 icacls 生效）；失败**如实返回 False**；`tests/test_private_fs.py` 用真机 `icacls` 断言"跳过收紧的新文件也已继承受限 ACL"、且"删后重建必须重收紧" |
| L2 | `MemoryCipher.generate(key_file=…)` **静默覆盖**已有密钥文件 → 存量数据永久读不回 | 默认拒绝覆盖，需显式 `overwrite=True` | 第二次调用抛 `FileExistsError` |
| L3 | `Sm4Cipher(key, iv)` 的 `iv` 形参**被完全忽略**（调用方以为能固定 IV，实际无效） | 移除该形参（宁可 TypeError，也不留「看似能用」的坑） | 传 iv 抛 `TypeError` |
| L4 | `set_master_key` **不校验长度**：错长度延后到首次加解密才以「填充错误」爆出，极难定位 | 入口即校验 16 字节；`None` 保留清空语义 | 错长度全 `ValueError`；`None` 仍可复位 |
| L5 | 密钥库目录 / 文件可能由历史版本以**默认权限**落盘 | boot 时 `_harden_paths()` 补收紧；失败 `logger.warning` 明说「当前仅依赖父目录 ACL」 | 收紧结果如实告警 |
| L6 | `keystore` 日志可能带出**主密钥 / 校验码**（日志会外流） | 日志只报指纹强度与来源名，不报任何长 hex | 捕获日志实测：无 ≥16 位 hex 出现 |
| L7 | `file_ops` 输出路径**可 `..` 穿越**（写任意位置），解出的明文落点不受控 | 输入 / 输出路径统一拒绝 `..` 穿越 | 两条路径均抛 `ValueError` |
| L8 | 指纹实为**型号级**（BIOS 厂商_型号），同型号机器指纹相同 → 密钥库文件拷走即可离线解封，与「仅本机可解封」的承诺不符 | 改为按「唯一性从高到低」取**第一个**可用标识（MachineGuid / machine-id / BIOS 序列号 → 型号兜底），并以 `fingerprint_strength()` **如实报出**用了哪一级 | 本机实测 `per-unit`（来源 `machine-guid`）；降级到型号级会 `logger.warning` |

**代价（不掩盖，三条；第 1、3 条已在 v0.5.1 缓解/修复）**：
1. ✅ **boot 变慢（已缓解）**：`_harden_paths()` 每次 boot 追加 3–4 次 `icacls` 子进程，实测
   boot 由基线 ~66ms 升到 ~150–220ms（其中 ~53–75ms 为该加固开销）。v0.5.1 加了「已收紧即跳过」
   标记（`harden_dir_once` / `harden_file_once`）后，同进程重复 boot 不再付该开销；本轮实测
   `vault.boot()` p50 由 131.5ms 回落到 **62.9ms**（新进程首次仍付一次，属一次性装配）。
2. **重装系统会改变指纹**：指纹改用系统级标识（MachineGuid 等）后，重装 OS 即变更，
   需用 32 位 hex 恢复密钥重新导入（恢复路径本来就存在，见 §5）。
3. ✅ **私有落盘 +15~22ms/次 —— v0.5.1 已修（保留披露以便回溯）**：L1 的 `icacls` 是**子进程**，
   原实现每次 `write_private_bytes` 都要付一次启动开销。回归实测：`write_private_bytes` 1KB
   由 0.13ms → 14.73ms（该项占 99%）；`file_ops.encrypt_file` 1MB 由 12.89ms → 35.41ms（占 **64%**）。
   **修法（已落地）**：按「同一对象只收紧一次」重写——目录级一次性收紧并给子项 `(OI)(CI)`
   继承位；文件级按**文件身份**（`st_dev, st_ino`）缓存；缓存判定失败即重收紧。四场景定标（本机，中位数）：

   | 场景 | 修复后 | 修复前 | 零 icacls 下限 |
   |---|---|---|---|
   | `write_private_bytes` 1KB（覆盖同路径） | **0.21 ms** | 15.98 ms | 0.20 ms |
   | `write_private_bytes` 1KB（每次新建） | 18.53 ms | 18.53 ms | 0.27 ms |
   | `encrypt_file` 1MB（覆盖同路径） | **14.16 ms** | 30.29 ms | 13.99 ms |
   | `encrypt_file` 1MB（每次新建） | 48.11 ms | 48.11 ms | 27.09 ms |

   即**覆盖写同一文件**的 icacls 残量降到 ~1%（1MB 场景 14.16 vs 下限 13.99 ms）；
   首次写仍是冷态（1KB 首次 17.4ms → 之后 0.39ms）。
   ⚠️ **已知边界（如实披露）**：*每次新建不同文件*（批量加密 N 个新文件、每次解密到新路径）
   仍需**逐文件**一次 icacls —— 因为那些是调用方给的任意目录，做目录级收紧会清掉该目录
   原有继承 ACE（越权副作用）。要彻底消掉它需把 icacls 子进程换成进程内原生 ACL API
   （`SetNamedSecurityInfo`），属后续可选项，本轮**未做**（不做过度工程）。
