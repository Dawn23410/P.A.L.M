## 1. 换装记录（对外 API 零变化）

- **C 底层库**：`tongsuopy 1.0.1`（铜锁/Tongsuo——OpenSSL 国密分支的 Python 绑定，
  Windows 预编译 wheel，含 `_tongsuo.pyd` C 扩展）。安装：`pip install "加解密内核[c]"`。
- **适配层**：新增 `palm_cryptokernel/backends.py`——探测 `tongsuopy` 成功即用 C，失败自动
  回退纯 Python gmssl（保底，声明依赖不删）。`backend_name()` / `is_c_backend()` 供日志与审计引用。
- **接线范围**：`sm4.py`（Sm4Cipher）、`sm3.py`（sm3_hash/sm3_int）、
  `vault/operations.py`（encrypt/decrypt_data、seal/unseal）全部走 backends。
  第一轮接线漏了 `sm3.py`，MemoryCipher 完整性标签仍走纯 Python（p50 2.6ms），
  补接后降到 0.053ms——**"只换一处"会留下隐形瓶颈，已全量接线**。
- **正确性三重验证**：
  1. GB/T 32907-2016 国标向量：gmssl ✓、tongsuo ✓（首块 `681edf34…` 逐位一致）；
  2. **两后端密文逐字节一致**（0/1/16/600/1500/65536B 全尺寸）；
  3. 双向互操作 + **存量旧密文兼容**（纯 Python 加密的历史数据，C 后端可解）。
- 过程中修正一个自引入缺陷：`seal_keystore/unseal_keystore` 曾误加"主密钥已就绪"
  前置检查——首次 boot 时主密钥尚未生成、正是被封印对象，已改回"只查底层可用性"。

## 2. 大文件低并发（vault.file_ops，含磁盘 IO，并发 1）

| 文件 | 操作 | p50 | tp999 | 吞吐 | 样本 n |
|---|---|---|---|---|---|
| 1MB | encrypt_file | 14.83ms | **29.14ms** | 67.3 MB/s | 20 |
| 1MB | decrypt_file | 27.78ms | **34.02ms** | 36.0 MB/s | 20 |
| 10MB | encrypt_file | 135.85ms | **154.30ms** | 73.6 MB/s | 5 |
| 10MB | decrypt_file | 136.29ms | **139.14ms** | 73.4 MB/s | 5 |
| 100MB | encrypt_file | 1436.56ms | 1436.56ms* | 70.6 MB/s | 2 |
| 100MB | decrypt_file | 1265.62ms | 1265.62ms* | 79.3 MB/s | 2 |
| 10MB | encrypt+decrypt @4线程 | 312.43ms | **337.69ms** | 124.0 MB/s 聚合 | 4 |

\* n=2 时 tp999 即最大值，样本不足仅供参考（大文件低并发场景下诚实做法是不硬凑分位）。

> 📅 **2026-09-23 复跑（C 后端装回本机）**：**≥10MB 各行与本文一致** —— 10MB 加密 141.6ms / 70.6 MB/s、100MB 加密 1325ms / 75.9 MB/s、10MB×4 线程 121.3 MB/s 聚合；
> 小文件高并发亦复现本文结论（1T/8T/32T 聚合吞吐 19228→5072→5094、10836→3127→3096，
> **线程不扩展、反而恶化**，GIL 串行化成立）。
> **唯 1MB 两行变差约 2 倍**（encrypt 29.06ms / decrypt 42.17ms）——不是加密变慢，
> 是权限加固新增的 `icacls` 子进程（≈15–22ms/次）在大文件上被摊薄、在 1MB 上占比过半，
> 见 §6。去掉该项后 1MB 加密回到 ~12.9ms。

**读法**：吞吐稳定在 **67–79 MB/s**（低于 SM4 纯吞吐 123–166，差额是 HMAC-SM3 完整性
+ base64 无（file 路径无 base64）+ 磁盘 IO + Python 胶水）。对比纯 Python 的 0.14 MB/s，
**100MB 从 ~12 分钟降到 1.4 秒**，大文件场景正式解禁。10MB 并发 4 聚合吞吐 124 MB/s
（≈并发 1 的 1.7×）——大块数据路径存在并行收益（IO 等待与大块 C 调用可交叠）。

## 3. 小文件高并发（per-op tp999；6000 op/档）

| 路径 | 线程 | p50 | p95 | p99 | **tp999** | 聚合吞吐 |
|---|---|---|---|---|---|---|
| MemoryCipher 600B 记忆条目 (enc+dec) | 1 | 0.053ms | 0.074ms | 0.137ms | **0.220ms** | 17431 op/s |
| MemoryCipher 600B | 8 | 1.639ms | 2.446ms | 2.856ms | **3.372ms** | 4735 op/s |
| MemoryCipher 600B | 32 | 6.588ms | 10.059ms | 11.686ms | **14.264ms** | 4683 op/s |
| vault encrypt+decrypt_data 1KB | 1 | 0.093ms | 0.188ms | 0.229ms | **0.336ms** | 9484 op/s |
| vault 1KB | 8 | 2.711ms | 3.635ms | 4.024ms | **4.577ms** | 2897 op/s |
| vault 1KB | 32 | 11.127ms | 15.032ms | 16.845ms | **19.318ms** | 2836 op/s |

**必须诚实说明：线程高并发不扩展、反而恶化。** 聚合吞吐 1T→8T→32T 不升反降
（17431→4735→4683 / 9484→2897→2836），per-op tp999 同步恶化（0.22→14.3ms）。
原因是 **GIL 串行化**：tongsuopy 为 pyca 风格绑定，小对象加解密期间不释放 GIL，
多线程只是排队轮转，还叠加调度与争用开销。

**生产建议（小文件）**：
- 单进程内**不需要**为加解密开多线程——单线程 9.4k~17.4k op/s 已远超记忆层写入速率
  （实测 VectorMemory add p50 49.6ms/条，即 ~20 op/s 量级，加密占比已趋近于零）；
- tp999 的正确用法：**并发 1 或低并发下 tp999 = 0.22~0.34ms**，这才代表真实用户尾延迟；
- 若未来确需并行加解密（如批量回填），走**多进程**而非多线程。

## 4. 安全回归（换后端后全部重跑，全 PASS）

round-trip（MemoryCipher/vault/file）· 篡改密文拒绝（HMAC-SM3）· 坏 PKCS7 拒绝 ·

## 6. 2026-09-23 复现、一处自家回归、以及它的修复

**复现结论**：本文 C 数字成立。跨后端**密文逐字节一致**已按 0 / 1 / 15 / 16 / 17 / 600 /
1500 / 65536 B 八个尺寸双向复核（C 加密→纯 Python 解、纯 Python 加密→C 解），
存量数据换后端不受影响；GB/T 32905-2016 / 32907-2016 国标向量两后端均对拍通过。

> **与 §0 取值的差异说明（避免两处数字打架）**：§0 记 SM3 392 MB/s、SM4-CBC 123–166 MB/s，
> 是本轮复测前的一轮取数；本轮（1MB 缓冲、无 base64）得 SM3 **436**、SM4-CBC **126 / 146**
> MB/s。两轮同量级，差异来自缓冲尺寸与运行抖动，**两轮口径都是"去 base64 纯吞吐"**，
> 不能与 §2 里含 base64 的 64KB 项（~56 MB/s）直接比。

### 6.1 回归（已修，保留披露以便回溯）

为修"密钥/明文以默认权限落盘"（见《安全与性能审计》§7 的 L1），
`_private_fs.write_private_bytes` 原先**每次落盘都调一次 `icacls`** 收紧 ACL，
而该调用是 Windows 子进程、**≈15–22 ms/次**：

| 场景 | 含 icacls | 去掉 icacls | icacls 占比 |
|---|---|---|---|
| `write_private_bytes` 1KB | 14.73 ms | 0.13 ms | **99%** |
| `file_ops.encrypt_file` 1MB | 35.41 ms | 12.89 ms | **64%** |

即**小文件写路径被这一项完全主导**；1MB 文件加解密从 ~12.9ms 被抬到 ~35ms。
注意这与"加密慢"无关——**去 base64 的纯吞吐是 126–146 MB/s**，慢的是权限收紧。

### 6.2 修复（v0.5.1，按候选 1 落地）

`_private_fs` 重写为「**同一对象只收紧一次**」，安全语义不变：
目录级收紧带 `(OI)(CI)` 继承位（自管目录内新建文件自动继承，不再逐文件 icacls）；
文件级按**文件身份**（`st_dev, st_ino`）缓存——文件被外部删除重建会拿到新身份，
缓存自动失效，**不存在"缓存说已收紧、实际已换文件"的裸奔**；收紧失败不写缓存、如实返回 `False`。
⚠️ 目录级**只用于自管目录**（密钥库/数据目录），绝不动调用方给的任意目录
（`/inheritance:r` 会清掉该目录原有继承 ACE，属越权副作用）。

四场景定标（本机中位数）：

| 场景 | 修复后 | 修复前 | 零 icacls 下限 |
|---|---|---|---|
| `write_private_bytes` 1KB（覆盖同路径） | **0.21 ms** | 15.98 ms | 0.20 ms |
| `write_private_bytes` 1KB（每次新建） | 18.53 ms | 18.53 ms | 0.27 ms |
| `encrypt_file` 1MB（覆盖同路径） | **14.16 ms** | 30.29 ms | 13.99 ms |
| `encrypt_file` 1MB（每次新建） | 48.11 ms | 48.11 ms | 27.09 ms |

**已知边界**：*每次新建不同文件*仍要逐文件一次 icacls（任意目录不能做目录级收紧）。
彻底消掉需用进程内原生 ACL API（`SetNamedSecurityInfo`）替代 icacls 子进程，本轮**未做**。
