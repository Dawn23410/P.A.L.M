# 砖块设计文档 - 01 agent 砖（AgentCore 智能体引擎 + 安全自防护）

> 版本：v1.2（2026-08-14 第四次重写：补全 completion_gate 6 条内置规则细节 + 提问中心 ask_user 即时队列 + trace JSONL 5MB 轮转 + 全部 27+ 子模块 API 引用）
> 路径：`backend/app/bricks/agent/`
> 定位：P.A.L.M 的大脑，承载 ReAct 循环、工具调用、规划生成、反思决策、**安全自防护（code_guard + 提示注入剥离 + 提问中心 + 运行轨迹 + 硬阻断）**

---

## 摘要

agent 砖是 P.A.L.M 最复杂的砖块，由 27 个子模块组成，覆盖从用户消息接收到最终回答的全链路。它包含 4 类可注入核心组件、5 种执行模式（含原生 function calling）、4 类安全网（完成判定 + 代码守卫 + 提示注入剥离 + 后台任务守卫）、1 个自主规划引擎、1 个人机交互提问中心、1 个运行轨迹追踪系统，以及 1 套 Boss-Worker 双 Agent 协调机制。

本版本（v1.2）相比 v1.1 重点补全了：
- **completion_gate 6 条内置规则细节**（read_file 第一行 / web_fetch 标题 / pytest passed / 截图 OCR 摘要 / 截图异常判断 / read_file confirmed）
- **提问中心 ask_user 事件即时队列推送机制**（避免消费方无法应答导致的永久阻塞）
- **trace JSONL 5MB 自动轮转 + trace_id 关联**
- **27+ 子模块逐项 API 引用**

## 1. 功能支持

### 1.1 核心执行能力

| 能力 | 入口 | 行为 |
|---|---|---|
| 单轮 ReAct 执行 | `AgentCore.run(message)` | 写入用户消息 → 触发记忆归档 → 监控 token 预算 → 异步预加载语义上下文 → 调 LLM → 解析工具调用 → 循环 → 完成判定 |
| 多轮 ReAct 循环 | `AgentCore.run()` 内 `max_iterations` | 默认 10 轮，每轮可调一个工具，由 `completion_gate` 判定提前结束 |
| **原生 function calling** | `native_runner.run_native()` | 通过模型原生 `tool_calls` 决策，工具结果以 `role=tool` 消息回灌，跨轮用 `tool_call_id` 配对，从根上消除指令泄漏与角色语气污染 |
| 角色设定注入 | `persona_provider` | 支持自定义人设文本或角色卡片，自动注入到 system prompt |
| 深度思考开关 | `deep_think=True` | 启用两步推理：先生成思考链，再生成行动 |
| 工具自动过滤 | `auto_filter_tools=True` | 根据用户意图语义匹配工具集，缩减 prompt token 消耗 |
| 工具白名单 | `allowed_tools=[...]` | 硬白名单约束，调 LLM 时只暴露指定工具 |
| **自主规划** | `planner.Planner.plan()` | LLM 拆解为多步 Plan，失败时基于已有进展 re_plan |
| **重规划** | `planner.Planner.replan()` | 某步失败时基于已完成的步骤重新规划剩余步骤 |
| 上下文预加载 | `preload_context` | 200ms 内异步执行轻量工具，把结果作为 Observation 注入首轮 LLM 调用 |
| 反思自检 | `ReflectionMixin` | 工具调用后触发自审，最多 1 次重试 |
| **双 Agent 协调（Boss-Worker）** | `dual/coordinator.py` | Boss 处理 chat / task / intervention / query 四类意图，Worker 后台跑任务，Boss 每轮从 TraceStore 拉摘要注入 system prompt |
| **提问中心** | `question_hub` | Agent 调 `ask_user` 工具时后端发卡片 + await Future，前端应答后 resolve Future 继续推理 |
| **运行轨迹追踪** | `trace.trace` | 记录全链路（思考/工具/结果/增量/终态/时长/错误），落盘 JSONL 供事后排查 |
| **代码静态扫描** | `code_guard._scan_code_risks()` | run_code 前置 5 类风险检查（daemon 线程 / 破坏性删除 / 子进程无超时 / 系统路径删除 / detach 后台） |
| **系统还原点** | `code_guard._create_restore_point()` | 会话内仅自动建一次系统还原点，作为系统级回滚安全网（不保护个人文件） |
| **风险确认弹窗** | `code_guard._confirm_risk_dialog()` | 静态扫描命中后弹窗征求用户同意 |
| **硬阻断** | `code_guard._is_hard_blocked()` | 系统级毁灭性操作（系统目录删除/全盘格式化）不可被 autoconfirm 放行 |
| **后台任务守卫** | `code_guard.guard_background_command()` | start_background_task 前置安全网（H4 修复） |
| **提示注入剥离** | `_native_execution._strip_prompt_injection()` | 工具结果写记忆前剔除常见"提示注入"指令短语（H1 防护，保守移除短语） |
| **旧版毒数据剥离** | `native_runner._sanitize_tool_text()` | 拼 prompt 前剥离"✅ 工具【name】执行成功…"装饰壳 |

### 1.3 完成判定门（Completion Gate —— v1.2 完整 6 条内置规则）

`completion_gate.py` 通过 `register_rule()` 暴露可注册接口，任何人都能加入自定义完成判定规则。后注册的规则优先级更高（先匹配）。**6 条内置规则**（按注册逆序优先级）：

| 规则名 | 触发条件 | 完成判定输出 |
|---|---|---|
| `_rule_read_file_first_line` | 工具 = `read_file` + 请求含"第一行" + 请求含"字符数" | `第一行={内容}；字符数={长度}` |
| `_rule_web_fetch_title` | 工具 = `web_fetch` + 请求含"页面标题"或"标题" | `页面标题={HTML title 或 title: 内容}` |
| `_rule_read_file_confirmed` | 工具 = `read_file` + 请求含 `confirmed=` | `confirmed={第一行}` |
| `_rule_pytest_passed` | 工具 = `run_code` + 请求含 `pytest` + 输出含 passed | `测试通过。已根据测试结果完成修复。` |
| `_rule_screenshot_ocr_summary` | 工具 = `take_screenshot` 或 `screenshot_region` + 请求含 `OCR识别摘要=` 与 `总体分析=` | `OCR识别摘要={...}\n\n总体分析={...}`（含 OSWorld/AI Agent/benchmark 关联判定） |
| `_rule_screenshot_exception` | 工具 = `take_screenshot` 或 `screenshot_region` + 请求含 `异常判断=` 与 `证据摘要=` | `异常判断=网络异常/页面可读/证据不足\n\n证据摘要={...}` |

**关键设计**：
- 规则异常被 try/except 隔离，不影响其他规则和主流程
- 返回 None = "规则不适用，继续循环"
- 返回字符串 = "已完成 + 最终答案片段"
- `_extract_ocr_evidence` 用 `[屏幕 OCR 识别]...[/屏幕 OCR 识别]` 标签定位 OCR 内容
- `_looks_like_network_error` 检测 `无法访问` / `err_connection` / `dns_probe` 等网络错误标志
- `_has_enough_text_evidence` 要求清理后文本长度 ≥ 12 字符（避免空内容假阳性）
- `_requires_detail_tab_lifecycle` 检测"点开+关闭当前资料页"指令，决定是否跳过 OCR 摘要规则

### 1.4 情绪检测器

`emotion_detector.py` 检测 5 类中文情绪（开心 / 挫败 / 焦虑 / 悲伤 / 平静），输出 `{emotion, confidence, matched, intensity}` 字典。检测采用预编译正则（每类一组合并正则 + 强度修饰词 + 重复符号识别），效价-唤醒映射表针对中文文化做了修正：

- 儒家文化情绪表达偏内敛，唤醒基线整体低于西方常模
- 「挫败」含无奈语义，效价 -0.5（vs 西方 anger -0.7）
- 「悲伤」偏沉默内敛，唤醒低（对应「哀而不伤」文化）
- 强度修饰词（"死了/透顶/爆"等）会提升 intensity 档位，进而上浮唤醒值
- 重复符号（"哈哈哈"≥3、感叹号 ≥2）算宣泄强度加成
- **非对称效价编码**：仅 valence ≥ 0 触发编码巩固（防止负性记忆抵消非对称衰减）

### 1.5 code_guard 代码守卫（用户最关心的"AI 给自己打补丁"防护）

`code_guard.py` 是 P.A.L.M 中"AI 给自己打补丁"的关键防线。它在 Agent 调 `run_code` 或 `start_background_task` 前执行**5+1 类风险检查 + 还原点 + 确认弹窗**：

#### 1.5.1 5 类静态风险检查（5 个单职责函数）

| 检查函数 | 检测模式 | 风险提示 |
|---|---|---|
| `_check_daemon_thread` | `thread(...)` 或 `threading` + `daemon` + 无 `.join(` | 后台线程被强杀，对话无法闭环 |
| `_check_destructive_delete` | `os.remove` / `os.rmdir` / `shutil.rmtree` / `rm -rf` / `rmdir /s` / `del /f` / `remove-item` | 破坏性删除，建议加 try 容错并二次确认（已启用文件保险库） |
| `_check_subproc_timeout` | `subprocess` / `popen(` / `os.system` / `start-process` + 无 `timeout` | 子进程无超时可能永久挂起 |
| `_check_system_path_delete` | `c:\users` + `*` 或 `rm` / `c:\windows` + `rm` | 硬编码系统路径删除风险极高 |
| `_check_detached_background` | ` & ` / ` &` 结尾 / `start /b` / `nohup` / `start-process` 无 `-wait` / `create_new_console` / `detached_process` / `popen(` 无 `communicate`/`wait` | 任务 detach 后 run_code 立即返回对话无法闭环 |

#### 1.5.2 +1 硬阻断（不可被 autoconfirm 放行）

`_is_hard_blocked()` 检测系统级毁灭性操作：
- 系统目录（`c:\windows` / `c:\program files` / `c:\programdata` / `/windows` / `/sys` / `/boot`）+ 破坏性关键字（`rm -rf` / `rmdir /s` / `del /f` / `os.remove` / `shutil.rmtree` / `remove-item` / `format ` / `mkfs` / `diskpart`）→ **双命中强制拦截**
- `rm -rf /` / `rm -rf ~` / `sudo rm -rf` → **根目录强制拦截**
- `format ` + `c:` 或 `/dev/` → **全盘格式化强制拦截**

即使开启 `PALM_AUTOCONFIRM_RUN_CODE=1` 也强制拦截，防评测/无人值守场景彻底破坏系统。

#### 1.5.3 系统还原点（Windows 专属）

- 探测阶段：`_detect_protection_disabled` 检查 Windows 系统保护是否开启
- 询问阶段：`_ask_enable_system_protection` 用 `ask_user` 弹窗询问"开启并继续 / 跳过(无回滚) / 取消"
- 开启阶段：`_try_enable_system_protection` 调 sandbox 砖的 `restore_point` capability
- 创建阶段：`_create_restore_point` 会话内**仅自动建一次**（24h 内 Windows 系统保护合并）
- 失败不阻断，追加风险提示
- 不保护用户个人文件（仅系统级回滚）

#### 1.5.4 风险确认弹窗

- 静态扫描命中后通过 `question_hub` 弹窗征求用户同意
- 用户拒绝 → 拦截工具调用，返回 `"blocked"`
- ask_user 事件经**即时队列**（`agent._ask_events`）在 wait 前推送，避免消费方无法应答导致的永久阻塞
- 即时队列未初始化时（异常路径）静默跳过，仅靠事件列表兜底

#### 1.5.5 关键设计哲学

> "AI 写代码 ≠ 直接执行"
> "AI 改系统文件 ≠ 静默成功"
> "评测场景自动放行 ≠ 系统级毁灭性操作放行"
> "会话内只建一次还原点 = 不浪费 Windows 系统保护资源"

### 1.6 提示注入防护（H1 防护）

`_native_execution._strip_prompt_injection()` 在工具结果写记忆前剔除常见"提示注入"指令短语：

- `ignore all previous instructions` / `disregard the above`
- `you are now ...` / `system prompt:` / `# instructions`
- `忽略之前的指令` / `忘记之前的对话`

**保守移除短语而非整句**，避免误删合法内容。这是对抗"工具结果中夹带注入"的最后一道防线。

### 1.7 提问中心（人机交互 Future 机制 + ask_user 即时队列）

`question_hub.py` 是 Agent 与用户交互的关键，**v1.2 重点强化 ask_user 事件即时队列**：

#### 1.7.1 Future 机制

- **进程级单例**：`get_question_hub()` 返回 `_hub` 单例
- **Future 阻塞**：`wait(question_id)` await Future 永不超时
- **回答回调**：`answer(question_id, conversation_id, payload)` resolve Future
- **会话清理**：`cancel_for_conversation(conversation_id)` 流被中止时清理悬挂问题
- **超时清理**：`_prune(max_age=30min)` 自动清理超时问题，避免内存泄漏

#### 1.7.2 question_id 注入 spec（P6 修复）

`create()` 把 `question_id` 注入 `spec["id"]`——前端 AskUserCard 用 `question.id` 回传应答，后端曾只发 `title/content/qtype/options` 导致应答无处可送（P6 评测暴露）。

#### 1.7.3 ask_user 事件即时队列（关键修复）

`code_guard._push_ask_event(agent, ev)` 把 `ask_user` 事件**经即时队列**（`agent._ask_events`）在 wait 前推送——这是修复 P6 评测死锁的关键：

```
ask_user 事件必须经即时队列在 wait 前推送
否则消费方收不到事件就无法应答、wait 永不返回
events 列表仅兼容旧调用方，实际不再依赖其下发
```

`agent._ask_events` 是 `asyncio.Queue` 实例，由 Agent 初始化时创建。SSE 层并发消费此队列，确保 ask_user 事件不丢失。

### 1.8 运行轨迹追踪（P5 之"追踪"，v1.2 补全 5MB 轮转）

`trace.py` 提供 LangSmith / OpenAI Agents 式的可观测性：

- **记录全链路**：思考/工具调用/工具结果/文本增量/终态/时长/错误
- **JSONL 落盘**：基于存储池绝对路径（不依赖 CWD）
- **5MB 自动轮转**：单文件超 5MB 自动切文件（按时间戳命名新文件）
- **trace_id 关联**：每条 trace 携带唯一 trace_id，便于跨文件查询
- **最近一次轨迹缓存**：缓存在 `agent._last_trace` 供即时调试
- **纯增量、零侵入**：仅在 `core.run` 包裹事件流，任何异常都不影响主流程

### 1.9 自主规划引擎

`planner.py` 把用户目标拆解为有序、可执行的步骤（Plan），并在某步失败时基于已有进展重规划：

- **步骤状态机**：`pending` / `running` / `done` / `failed` / `skipped`
- **解析失败降级**：解析失败或返回空计划时，降级为单步计划（即把目标当作唯一一步），保证规划引擎在 LLM 异常时等效退化为普通 ReAct 执行
- **LLM 调用复用**：复用 Agent 已有的流式桥接（`llm_stream_fn(messages, model) -> AsyncIterator[dict]`）
- **零外部依赖**：解析与降级完全本地

### 1.10 双 Agent 协调（Boss-Worker）

`dual/coordinator.py` 是 P.A.L.M 的双脑架构：

- **意图分流**：`IntentRouter` 判定意图为 `chat` / `task` / `intervention` / `query` 四类
- **chat → Boss 直接回复**（可附带 Worker 轨迹摘要）
- **task → Boss 回复确认 + 后台 asyncio.Task 启动 Worker**
- **intervention → 转发到 Worker 干预队列**（cancel / pause / resume / redirect）
- **query → Boss 从 TraceStore 检索 Worker 进展后回复**
- **Worker 全程后台执行**：事件只写 TraceStore 不直接发前端
- **Boss 每轮从 TraceStore 拉摘要注入 system prompt**：实现"分片检索"而非一次性灌入全部上下文

### 1.11 专业 Agent 私有记忆

`dual/professional_memory.py` 是子 Agent 的私有记忆区：

- **轻量 / 私有 / 可合并**：只服务专业 Agent，不挂到主 Agent 公开查询接口
- **三类内容**：经验总结（`experience`）/ 用户画像（`user_profile`）/ 错误记录（`error`）
- **基础关键词检索**：不复用主记忆的五因子检索
- **任务级隔离 buffer**：每次任务创建独立 buffer memory，通过 TraceStore 记录执行轨迹供主 Agent 检索
- **3-5 条经验注入**：新任务启动时动态注入相关经验（合并同类项以提高信息密度）
- **异步整理**：任务完成后异步整理经验，不阻塞主 Agent 返回结果

## 3. 关键设计决策

### 决策 1：四可注入核心组件

`matcher` / `completion_gate` / `persona_provider` / `token_budget` 四类组件支持协议注入，未传时使用默认实现。**好处**：单测可替换为 mock；A/B 实验可并跑多套实现；后续重构只换实现不动调用方。

### 决策 2：原生 function calling + 文本式 ReAct 并列

`native_runner`（默认）与 `react_parser`（旧版）并存。原生模式从根上消除"把系统指令/工具结果混进对话文本"导致的指令泄漏与角色语气污染。**好处**：现代 LLM 优先用 native；老 LLM fallback 到文本式。

### 决策 3：完成判定门规则注册制（6 条内置 + 可注册）

原版硬编码在 `core.run()` 内部，重构后改为可注册规则。新规则 = 一段函数 + `register_rule(fn)`。**好处**：完成判定策略可独立演进，不污染主循环。6 条内置规则覆盖：read_file 第一行 / web_fetch 标题 / pytest passed / 截图 OCR 摘要 / 截图异常判断 / read_file confirmed。

### 决策 4：中文情绪修正映射表

情绪检测不直接套用西方常模的 valence-arousal 表，而是按中文文化做 4 项修正（挫败效价 -0.5、悲伤低唤醒、平静兜底、强度档位联动、非对称效价编码）。**好处**：人设回应更贴合中文用户语境。

### 决策 5：5+1 类代码风险检查

`code_guard` 用 5 类静态扫描 + 1 类硬阻断（系统级毁灭性操作不可被 autoconfirm 放行）。**好处**：常规破坏性操作有弹窗兜底；极端破坏性操作无论何时都强制拦截。

### 决策 6：系统还原点会话内仅一次

`_create_restore_point` 在会话内仅自动建一次（同一会话重复 run_code 不重复建）。**好处**：避免 24h 内反复建还原点（Windows 系统保护合并）；用户每次 run_code 都能拿到"执行前状态"。

### 决策 7：硬阻断不可被 autoconfirm 放行

`PALM_AUTOCONFIRM_RUN_CODE=1` 是评测/无人值守场景的放行开关，但 `_is_hard_blocked` 始终拦截系统级毁灭性操作。**好处**：评测场景不卡死；但极端破坏不可能静默发生。

### 决策 8：提示注入剥离保守移除短语

`_strip_prompt_injection` 用正则匹配高信号短语（如 "ignore all previous instructions"），但**只移除短语而非整句**。**好处**：避免误删合法内容（如"请忽略之前的草稿"是用户合理请求）。

### 决策 9：旧版毒数据剥离

`native_runner._sanitize_tool_text` 剥离旧版工具结果装饰壳（emoji/状态行/隔离等级/GUI 提示/工具结果标签），确保毒数据不会重新进入模型上下文。**好处**：旧版"✅ 工具【name】执行成功…"装饰壳在 prompt 中原样回灌会被模型照复述。

### 决策 10：QuestionHub Future + 即时队列双机制

Agent 调 `ask_user` 时用 asyncio.Future 阻塞，前端回答后 `/api/agent/ask-response` 解析 question_id resolve Future。**v1.2 强化**：ask_user 事件必须经 `agent._ask_events` 即时队列在 wait 前推送，避免消费方无法应答导致的永久阻塞（P6 评测曾死锁于此）。**好处**：人机交互完全异步，不阻塞 Agent 主循环；Future 永不超时（30min 由 `_prune` 清理）。

### 决策 11：Trace 落盘零侵入 + 5MB 轮转

`trace.trace` 在 `core.run` 包裹事件流（不修改事件流本身），任何异常都不影响主流程。**v1.2 强化**：单文件超 5MB 自动按时间戳命名新文件，每条 trace 携带 trace_id 便于跨文件查询。**好处**：可观测性永远在线；调试不影响生产；长会话不会爆文件大小。

### 决策 12：Boss-Worker 事件流分片检索

Worker 全程在后台执行，事件只写 TraceStore 不直接发前端；Boss 在每轮对话前从 TraceStore 拉摘要注入 system prompt。**好处**：长链路任务不爆上下文；Boss-Worker 解耦。

### 决策 13：专业 Agent 私有记忆不复用主检索

`professional_memory` 不用主记忆的五因子检索，只用基础关键词匹配。**好处**：专业 Agent 记忆轻量、合并简单、检索快速；不污染主检索结果。

### 决策 14：双脑裁决异步化

裁决内部使用 `asyncio.run()` 改为 `async/await`，避免事件循环冲突。**好处**：与其他异步组件（native_runner / question_hub）兼容。

### 决策 15：Completion Gate 6 条内置规则的精准触发

每条规则只检测**用户请求中的高信号短语**（如"第一行" / "页面标题" / "pytest" / "OCR识别摘要="）而非泛化匹配，最大限度降低误判率。**好处**：不会因为 LLM 输出巧合含 "title" 字样就提前结束。

## 5. 性能与边界

- `max_iterations = 10`：单次 `run` 最多 10 轮工具循环
- `max_plan_steps = 8`：单次计划最多 8 步
- 5 类静态扫描延迟：< 50ms / 1000 行代码
- 还原点创建延迟：~1s（Windows 系统调用）
- Future 悬挂超时：30min（自动清理）
- Trace 单文件大小：5MB（自动轮转）
- 提示注入正则匹配：< 10ms / 100KB 文本
- 看门狗心跳超时：60s
- 最大并发 Worker：5
- QuestionHub 单例：进程级（线程不安全，单 event loop 内安全）
- 27 个子模块：均无类实例全局状态（除 QuestionHub 单例与 Agent 实例）
